# AGID Hybrid Architecture

Last updated: 2026-06-03

## Decision

AGID should use a hybrid model:

- **Central quality layer** improves address evidence, postal lookup, source scoring, building/place/map-feature enrichment, and conflict handling.
- **Device layer** keeps private address records, QR payloads, settings, and offline workflows usable without server access.
- **SDK layer** owns deterministic AGID encoding/decoding so apps, drones, terminals, and external systems can use AGID freely.
- **Open-data-pack layer** carries versioned open-source geography and postal metadata for offline or low-connectivity environments.

This avoids making the central server a hard dependency for AGID itself, while still letting the product become much better when online.

## AGID/AOID Split

The hybrid model starts from the AGID/AOID boundary:

- **AGID** is the public location, address, building, and public map-feature layer. It can be generated by SDKs and devices, shared publicly, enriched with public building/place/address/map-feature evidence, cached in open-data workflows, and improved by central quality services.
- **AOID** is the owner-controlled private delivery layer. It can include room, recipient, phone, private access notes, and delivery instructions, so it stays local-first and uses central sync only after explicit owner consent.

The central server can govern AGID specification quality, postal evidence, geography evidence, and public source packs. It must not become the public owner of AOID records. AOID updates and AOID QR regeneration are owner-only operations.

AOID sync uses a stricter rule than ordinary registered-address display:

- device/local storage may contain the full AOID record,
- public QR and public API surfaces expose only an AOID reference handle plus linked AGID,
- central/cloud sync can accept AOID only as an owner-device encrypted envelope with owner and device key ids,
- unencrypted AOID payloads in a sync queue are reduced to a public descriptor that says an encrypted payload is required.
- public AOID QR scans are treated as references, not proof that the scanning device owns the AOID.

## Communication Split

AGID communication is public-infrastructure communication. It is allowed to move through REST, OpenAPI clients, SDKs, QR, public caches, source packs, and job-status streams because it carries public location/address/building/map-feature evidence and must not contain private recipient data.

AOID communication is owner-private communication. It stays on the device by default. Network communication is limited to reference handles on public surfaces and encrypted envelopes on private sync surfaces.

| Surface | AGID role | AOID role |
| --- | --- | --- |
| Public API | Grid, postal, geocoding, building, map-feature, quality, and evidence lookup | Reference handle plus linked AGID only |
| SDK | Offline deterministic core, public source-pack reads | Local owner payload support; no ownership grant |
| QR | Public location card or public address reference | Public reference or private full transfer between trusted owner devices |
| Sync queue | Saved public grid references and descriptors | Owner-consented encrypted payload only; plain payload is redacted or rejected |
| SSE / realtime | Public job status and quality progress | Status metadata only; never plaintext private fields |
| Cache/data pack | Public/open evidence can be cached or packaged | No public cache and no open data export |

This split means an integration can use AGID freely without asking the central server for permission, while AOID requires owner consent and cryptographic protection before it crosses a network boundary.

## Rules

1. AGID core math must work in SDKs and on-device without central approval.
2. Central services may upgrade quality, confidence, and autofill, but should not be required to create or decode an AGID.
3. Registered addresses, AOIDs, and user settings are private records. They can sync only through explicit private sync paths.
4. Personal address records must never be pushed into a public or distributed data layer.
5. Postal APIs, OSM/OpenFreeMap/Overture, national GIS sources, and generated data packs are evidence sources, not a replacement for manual confirmation in weak-data regions.
6. SDK packages should consume the same AGID core model and optional source packs, not web-app-only behavior.

## Runtime Modes

- `sdk-portable`: deterministic grid and SDK functions run anywhere.
- `local-first`: local DB, local cache, QR, and manual entry stay usable offline.
- `central-assisted`: central service improves the local result when online.
- `central-verified`: central evidence and confidence can earn a verified/stronger badge.
- `read-through-cache`: postal or place lookup checks central/open APIs, then caches locally.
- `manual-required`: the app can display a result, but the confidence is not strong enough to pretend it is verified.

## Implementation Touchpoints

- `src/lib/hybridArchitecture.ts` defines workflow policies and runtime decisions.
- `src/lib/addressIdentity.ts` defines the AGID/AOID public/private boundary.
- `src/lib/aoid.ts` defines AOID local-first normalization, public references, encrypted sync envelopes, and revocation.
- `src/services/HybridQualityService.ts` calls central quality when it improves a workflow, and falls back to local policy when unavailable.
- `POST /api/v1/hybrid/quality` returns the same policy/decision envelope through the standard AGID server result.
- `GET /api/v1/openapi.json` exposes the public integration contract. Legacy `/api` routes remain compatibility aliases.
- `src/lib/syncQueue.ts` exposes the hybrid policy for each sync entity type.
- IndexedDB/localStorage remain the local-first storage path.
- Server APIs can be attached later to the workflows that already declare `quality-upgrade`, `verification-source`, or `optional-private-sync`.
