# 住所写像論 日本語版 v1 第12章 追加・編集差分案

対象: `docs/address-morphism-theory-ja-v1-master.md` 第12章「履歴グラフと住所保存則」

目的: 第12章を、検証済みのLean命題、PID lifecycle proof、履歴監査モデルに合わせて強化する。

## 1. 編集方針

第12章では、「住所保存則」を強く言いすぎないことが最重要である。

推奨する章の中心文:

> 住所保存則とは、住所が必ず消滅しないという自然法則ではない。AMTにおける住所保存則とは、住所参照の変化を削除や上書きで処理せず、履歴グラフ上の追加エッジ、分岐、統合、失効、訂正、対応不明として記録し、受理済みの履歴トレースを保持するという設計原理である。

これにより、Leanの `LineageGraph`、`LineageExtends`、`append_only_lineage_preserves_*` と対応する。

## 2. 12.1に追加する定義

現在の \(G_H=(V_H,E_H)\) の直後に、次を追加するとよい。

追加本文:

> 本稿では、履歴グラフの更新を原則として append-only とみなす。すなわち、新しい証拠や訂正が追加されたとき、旧グラフで受理されたノードやエッジは削除されず、新しいグラフに継承される。
>
> \[
> G_H \preceq G'_H
> \]
>
> は、\(G'_H\) が \(G_H\) の履歴拡張であることを表す。このとき、
>
> \[
> V_H\subseteq V'_H,\qquad E_H\subseteq E'_H
> \]
>
> が要求される。

補足:

この記述はLeanの `LineageExtends` と対応する。

## 3. 12.2の履歴エッジを整理する

現在の表はよい。より論文らしくするなら、エッジを次の4群に分ける。

| 群 | エッジ | 用途 |
| --- | --- | --- |
| 表記変化 | `renamed_to`, `corrected_to` | 表面表現や誤登録の更新 |
| 構造変化 | `split_into`, `merged_into` | 分割、統合、再開発 |
| 状態変化 | `retired`, `superseded_by`, `reassigned` | 失効、置換、再割当 |
| 運用変化 | `relocated_to`, `virtualized_as` | 社会的移転、災害時住所、仮想住所 |

追加本文:

> 履歴エッジは、住所表記の変化だけでなく、実体構造の変化、PID状態の変化、配送運用上の変化を区別する。特に `reassigned` は、同じ住所表現が別の実体へ再利用されたことを示すため、単なる `renamed_to` とは異なる。

## 4. 12.3に非関数性の定理を追加する

現在の \(L\subseteq X_{\mathrm{old}}\times X_{\mathrm{new}}\) は正しい。ここにLean検証済みの命題を追加する。

追加本文:

> 命題12.1 分割非関数性
>
> ある旧住所状態 \(x\in X_{\mathrm{old}}\) が、二つの異なる新状態 \(y_1,y_2\in X_{\mathrm{new}}\) へ分割されるなら、その遷移は単一関数
>
> \[
> f:X_{\mathrm{old}}\to X_{\mathrm{new}}
> \]
>
> として表せない。
>
> 証明の要点は、関数は同一入力に対して一つの出力しか返せないことである。もし \(f(x)=y_1\) かつ \(f(x)=y_2\) なら、\(y_1=y_2\) でなければならない。しかし分割では \(y_1\ne y_2\) であるため矛盾する。

検証対応:

```text
functional_transition_cannot_represent_split
```

## 5. 12.4の住所保存則を弱めて強くする

現在の本文はすでに「絶対法則ではない」と書けている。さらに、保存される対象を明確化する。

追加本文:

> ここで保存されるのは、住所そのものの物理的存在ではなく、受理済みの参照状態、遷移、履歴トレースである。したがって住所保存則は、現実世界における存在保存ではなく、AMTが管理する履歴表現の保存性である。

続けて、定理風に書く。

> 命題12.2 append-only履歴保存
>
> \(G_H\preceq G'_H\) ならば、\(G_H\) の既存ノード、既存エッジ、有限履歴トレースは \(G'_H\) でも保存される。

根拠:

```text
append_only_lineage_preserves_node
append_only_lineage_preserves_edge
append_only_lineage_preserves_trace
```

## 6. 「対応不明も履歴情報」を公理化する

12.4の「対応不明も履歴情報である」は重要なので、独立した小節にしてよい。

追加小節案:

### 12.x 対応不明の明示性

追加本文:

> AMTでは、対応不明を単なる欠落として扱わない。後継住所が不明である、行政資料が矛盾する、災害や紛争により対応関係が確認できない、非公式地名の継承が追跡できない、といった状態は、履歴グラフ上の明示的状態として記録する。
>
> これは、何も記録しないこととは異なる。何も記録しない場合、後続の解決器は「未調査」「資料欠落」「対応不明」「存在しない」を区別できない。対応不明を明示すると、後続の候補生成、再検証、監査、利用者表示で安全な保留が可能になる。

追加表:

| 状態 | 意味 |
| --- | --- |
| `unknown_successor` | 後継が不明 |
| `evidence_conflict` | 出典同士が矛盾している |
| `retired_without_successor` | 失効したが後継がない |
| `temporarily_virtualized` | 一時的に仮想住所へ写像された |
| `needs_reverification` | 再検証対象 |

## 7. 12.5 PID継承をPID lifecycleへ接続する

12.5の後に、実装検証済みのPID lifecycleモデルを入れるとよい。

追加本文:

> PID継承は、単なるPID文字列の維持ではない。AMTでは、PIDの履歴操作を少なくとも `history-update`、`merge`、`split` に分ける。

追加表:

| 操作 | 意味 | 必要条件 |
| --- | --- | --- |
| `history-update` | 同一PIDの履歴rootを進める | sequenceが進む、event countが一致する |
| `merge` | 複数PIDを一つへ統合する | source PID retire、target lineageがsourceを含む |
| `split` | 一つのPIDを複数へ分割する | source PID retire、target lineageがsourceを含む、partition非重複 |

追加本文:

> mergeでは、統合元PIDをretireしなければ、同じ参照対象に複数の永続参照が残る。splitでは、分割元PIDをretireし、分割先PID群へlineageを接続しなければ、古い過剰統合が残り続ける。

検証対応:

```text
pidLifecycleProof.test.ts
```

## 8. 12.6 社会的連続性との境界を明確化する

第13章へ接続するため、12.6の最後に次を足すとよい。

追加本文:

> 履歴グラフは、社会的連続性を表現できるが、社会的連続性を物理的同一性へ還元しない。たとえば会社が移転した場合、会社主体の履歴は継続しても、旧物理拠点と新物理拠点は別ノードとして扱われる。この区別をしないと、配送先、登記、災害支援、本人確認で誤った同一視が起きる。

第13章への橋渡し:

> 次章では、この社会的連続性を住所同一性の一成分として扱う。ただし、第12章の結論としては、社会的連続性も履歴グラフに接続される一種類のエッジであり、地理的同一性とは区別される。

## 9. 12.7 災害時住所と仮想住所のリスク条件を追加する

現在の記述はよいが、リスク条件を明示すると実装に近くなる。

追加本文:

> 災害時住所や仮想住所は、通常住所よりも短い有効期間、明確な発行者、失効条件、再検証条件を必要とする。仮想住所を永続住所と同じように扱うと、支援詐欺、追跡リスク、旧避難所への誤配送、失効済み支援IDの再利用が起きる。

追加表:

| 条件 | 目的 |
| --- | --- |
| `valid_from`, `valid_until` | 仮想住所の有効期間 |
| `issuer` | 誰が仮想住所を発行したか |
| `revocation_condition` | いつ失効するか |
| `source_freshness` | 情報が古すぎないか |
| `privacy_level` | 被災者や避難者の安全保護 |
| `delivery_scope` | 支援物資、医療、行政通知など用途 |

## 10. 12.8 訂正モデルを強化する

現在の「削除ではなく訂正エッジ」は正しい。さらに、訂正が履歴を壊さないことを明確化する。

追加本文:

> 訂正は、過去の履歴をなかったことにする操作ではない。訂正は、旧主張と新主張の関係を `corrected_to` として追加し、どの時点で、どの出典に基づき、どの方針で訂正されたかを記録する操作である。これにより、過去の誤解決を監査でき、将来の候補生成で同じ誤りを繰り返しにくくなる。

追加表:

| 訂正対象 | 訂正エッジ | 目的 |
| --- | --- | --- |
| 誤住所表記 | `corrected_to` | 正規表記へ接続 |
| 誤PID | `superseded_by` | 新PIDへ置換 |
| 誤統合 | `split_into` | 別実体へ分離 |
| 誤分割 | `merged_into` | 同一実体へ統合 |
| 誤履歴 | `corrected_to` + audit note | 監査可能な訂正 |

## 13. 章末に置く命題群

### 命題12.1 append-onlyノード保存

append-onlyな履歴拡張では、旧履歴グラフで存在した住所状態は新履歴グラフでも存在する。

### 命題12.2 append-onlyエッジ保存

append-onlyな履歴拡張では、旧履歴グラフで存在した履歴エッジは新履歴グラフでも存在する。

### 命題12.3 append-onlyトレース保存

append-onlyな履歴拡張では、旧履歴グラフで成立した有限履歴トレースは新履歴グラフでも成立する。

### 命題12.4 分割非関数性

一つの旧住所状態が二つ以上の異なる新状態へ分割される場合、旧住所から新住所への対応は単一関数では表せない。

### 命題12.5 PID lifecycle安全性

PID merge/splitは、source retire、lineage保存、partition非重複を要求しなければならない。

## 14. 避けるべき表現

| 避ける表現 | 理由 | 修正案 |
| --- | --- | --- |
| 住所は消滅しない | 記録喪失や失効がある | 住所参照の変化を履歴グラフに記録する |
| 旧住所は新住所へ写像される | split/mergeで一意でない | 関係または履歴グラフで扱う |
| PIDは永続的に同じ対象を指す | 建替え、分筆、誤発行がある | PIDは履歴グラフ上で継承、失効、merge、splitされる |
| 訂正は削除でよい | 監査不能になる | `corrected_to` として記録する |
| 対応不明は空欄でよい | 未調査と不明が混ざる | 対応不明を明示状態にする |

## 15. 最終判断

第12章は、住所写像論の中でかなり重要な章である。

修正の中心は、住所保存則を絶対法則から履歴グラフの保存性へ変えることである。これにより、第12章はLean検証、PID lifecycle proof、PID発行監査、第13章の社会的連続性へ自然につながる。

採用優先度:

| 変更 | 優先度 |
| --- | --- |
| 住所保存則をappend-only履歴保存に弱める | 最優先 |
| 分割非関数性命題を追加 | 最優先 |
| 対応不明の明示性を小節化 | 高 |
| PID lifecycle表を追加 | 高 |
| 災害時住所・仮想住所の有効期間と失効条件を追加 | 中 |
| 訂正エッジの監査可能性を強化 | 中 |
