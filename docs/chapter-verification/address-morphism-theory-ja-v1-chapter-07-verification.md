## 1. 第7章の位置づけ

第7章は、AMTを実際に動かす中核機構を定義する章である。

第6章では、非単射観測、候補欠落、射影損失、正規化衝突、文脈衝突により、条件なしの完全単一解決器が存在しないことを示した。第7章は、その限界を受けて、住所解決を一回の変換ではなく、多段の写像連鎖として設計する。

第7章の基本図式は次の通りである。

```text
表面表現
  -> 解析
  -> 展開
  -> 候補生成
  -> 構造比較
  -> クラスタリング
  -> 評価
  -> 解決または保留
  -> PID発行または非発行
  -> 履歴更新
```

この連鎖で最も重要なのは、各段階が「情報を捨てる処理」ではなく「証拠を構造化して次段へ渡す処理」であることだ。正規化、翻訳、検索、クラスタリング、評価はいずれも有用だが、どれか一つだけで住所同一性を決めると、第6章の反例にぶつかる。

## 5. 主張別検証

## 5.1 CH07-C01 写像連鎖としての住所解決

第7章の基本主張は正しい。第6章の不可能性定理により、表面住所を直接一つの実体へ変換するモデルは安全ではない。したがって、AMTは次の段階を明確に分離する必要がある。

| 段階 | 役割 | 失敗時の安全策 |
| --- | --- | --- |
| 解析 | 入力を証拠へ分解する | 解決しない。証拠を保持する。 |
| 展開 | 別名、翻訳、旧名、自然地理名を増やす | 展開候補を出典つきで管理する。 |
| 候補生成 | 対象候補を集める | 候補不足なら未解決にする。 |
| 構造比較 | 候補間・入力候補間の差を測る | 文字列一致だけで決めない。 |
| クラスタ | 同一対象らしい候補をまとめる | 過統合を避ける。 |
| 評価 | 証拠、品質、履歴、リスクを合成する | 閾値とマージンを使う。 |
| 解決または保留 | 最終状態を返す | 曖昧なら発行しない。 |
| PID発行 | 永続参照を作る | 強いゲートを通す。 |
| 履歴更新 | 変化を記録する | append-onlyまたは監査可能にする。 |

この構成は、実装の `addressMorphism`, `addressMorphismNetwork`, `pidIssuanceAudit`, `pidLifecycleProof` と整合している。

## 5.2 CH07-C02 解析写像

本文の解析写像

```text
pi_t : S_t -> T_t
```

は、表面表現を構造化トークンへ変換する写像として有効である。ただし、実務上は解析結果が一つとは限らない。複数の言語、旧住所、新住所、自然地理名、建物名、階、入口、相対位置が同時に出るため、次のような集合値写像または証拠束として書くとより正確である。

```text
pi_{c,t} : S_t -> EvidenceBundle_t
```

または

```text
pi_{c,t} : S_t -> P_f(T_t)
```

ここで `P_f` は有限集合を表す。無限の冪集合ではなく、実装可能な有限証拠集合として扱う方が安全である。

解析段階で一意解決してはいけない、という本文の主張は正しい。

## 5.3 CH07-C03 展開写像

本文の展開写像

```text
epsilon_{c,t} : T_t -> 2^{T_t}
```

は、検索能力を高めるモデルとして妥当である。実装テストでは、地名検索言語がアプリ設定や住所表示言語から独立していること、ネイティブ名、別名、アクセント除去、ローマ字、誤字候補、島名記述子が検索展開に含まれることを確認している。

これは、以前の設計方針である「地名検索はどんな言語でもできるだけ検索能力を高くし、アプリ設定や住所表示言語とは分ける」と整合する。

ただし、展開は候補衝突を増やす。本文では次を明記するとよい。

> 展開写像は再現率を高めるための写像であり、同一性を確定する写像ではない。展開された各トークンには、出典、言語、変換規則、信頼度、時刻を付与する。

## 5.4 CH07-C04 候補生成写像

本文の候補生成写像

```text
Gamma_{c,t}: 2^{T_t} -> 2^{X_t}
```

は、第6章の候補欠落補題とよく接続している。Leanの `missing_candidate_prevents_issue` により、候補集合にない対象は安全に発行できないことが支持されている。

実装では、公式郵便、Google libaddressinput、Open Location Code、自然地理、海・山などの文脈が候補強化に使われている。

修正点として、候補集合も無限集合ではなく有限集合として書くとよい。

```text
Gamma_{c,t}: P_f(T_t) -> P_f(X_t^{known})
```

ここで \(X_t^{known}\) はAMTが扱える既知実体集合である。理論上の世界全体 \(X_t^{world}\) と、実際に候補生成できる \(X_t^{known}\) を混同しない方がよい。

## 5.5 CH07-C05 構造比較

本文の構造的非類似度

```text
D_{c,t}: X_t x X_t -> R_{\ge 0}
```

は、第5章の形式的準備と整合している。ただし、`D` は通常の距離とは限らない。文脈によって非対称になり得るし、三角不等式を満たすとは限らない。

実装では、方向付きの構造距離を扱い、クラスタリング用には `structuralDissimilarity` として対称化した値を使っている。これは本文に反映した方がよい。

推奨表現:

> \(D_{c,t}\) は数学的な距離とは限らない。クラスタリングで対称性が必要な場合には、方向付き非類似度から対称化された \(\bar{D}_{c,t}\) を定義して用いる。

## 5.6 CH07-C06 クラスタリング

本文の

```text
Pi_{delta,c,t}(C) in Partitions(C)
```

は分かりやすい。ただし、閾値による類似性が同値関係になるとは限らないため、常に厳密な分割と書くと強すぎる。

実装テストでは、近い候補が連鎖して遠い候補まで統合される「過連結」を防ぎ、クラスタを有界に保つことが確認されている。

したがって、本文では次のように書くと安全である。

```text
Pi_{delta,c,t}: P_f(X_t) -> ClusterFamily_t
```

`ClusterFamily` は、用途に応じて分割、被覆、または有界クラスタ族として定義できる。第9章で厳密化するなら、第7章では「クラスタ族」と書く方がよい。

## 5.7 CH07-C07 評価

本文の評価関数

```text
E_{c,t}: K -> R
S_{c,t}: K -> [0,1]
```

は有効である。ただし、エネルギー \(E\) と支持度 \(S\) は向きが逆になりやすい。低いエネルギーが良いのか、高いスコアが良いのかを明確にする必要がある。

Leanの `ScoreSelectable` は、評価値、閾値、マージンを明示することで、近接タイを強制解決しないことを支える。実装テストでも、近接タイは `ambiguous` になり、証拠不足は `unresolved` になる。

推奨表現:

> 評価関数は真理を返す関数ではない。評価関数は、候補クラスタが発行可能なほど十分に支持されているか、二番手から十分に離れているか、品質と鮮度とリスクが許容範囲かを判定するための規則である。

## 5.8 CH07-C08 解決または保留

本文の解決結果型は、`resolved`, `ambiguous`, `unresolved`, `rejected`, `conditional` を含んでいる。

Lean中核では、現在次の四状態が形式化されている。

```text
resolved
ambiguous
unresolved
rejected
```

したがって、`conditional` を本文で使う場合は、次のどちらかを選ぶ必要がある。

| 選択肢 | 内容 | 推奨 |
| --- | --- | --- |
| 条件付き保留として扱う | `unresolved` または `ambiguous` に再検証条件を付ける。 | 現時点で推奨。 |
| 型を拡張する | `conditional(requirement)` をLeanと実装に追加する。 | 第10章以降で検討。 |

第7章では、次のように書くと安全である。

> `conditional` は、現時点では独立した解決状態というより、再検証条件や追加入力条件を持つ保留状態として扱う。

## 5.9 CH07-C09 PID発行または非発行

本文の「候補表示、解決結果、PID発行を分ける」という主張は非常に重要であり、強く採用できる。

Leanの `IssueAdmissible` は、PID発行に必要な条件をまとめている。

| 条件 | 意味 |
| --- | --- |
| 候補所属 | 発行対象が候補集合に含まれる。 |
| 評価閾値 | 候補クラスタが十分に支持される。 |
| マージン | 二番手から十分に離れている。 |
| 品質 | 国、地域、言語、自然地理、出典の品質が十分。 |
| 鮮度 | 古い住所や失効データではない。 |
| 衝突リスク | 有限PIDの衝突リスクが予算内。 |

実装のPID監査テストでは、候補生成、クラスタリング、未解決ゲート、履歴更新、PID発行を通過したことを証明し、未解決結果では監査証明を出さないことが確認されている。

## 5.10 CH07-C10 履歴更新

本文では、履歴更新を写像連鎖の末尾に置いている。この方向は正しい。

ただし、履歴更新は単なるログではない。旧住所、新住所、分割、統合、再開発、失効、再割当、PID merge/split を扱うため、履歴グラフまたは監査可能なイベント列として扱う必要がある。

PID lifecycle tests では、履歴更新、PID merge、PID split が、秘密の履歴ルートや候補割当を公開せずに検証できることを確認している。

第7章では概略でよく、詳細は第12章に送るのがよい。

## 6. 可換図式として入れるべき全体図

第7章には、次の図式を入れるとよい。候補表示、解決、PID発行、履歴更新を別ノードにすることが重要である。

```text
S_t
  -- pi_{c,t} -->
EvidenceBundle_t
  -- epsilon_{c,t} -->
ExpandedEvidence_t
  -- Gamma_{c,t} -->
CandidateSet_t
  -- D_{c,t}, Pi_{delta,c,t} -->
ClusterFamily_t
  -- E_{c,t}, threshold, margin -->
ResolutionOutcome_t
  -- issue gate -->
PID or NonIssue
  -- history update -->
H_{t+1}
```

この図式では、次の分離が見える。

| 分離 | 理由 |
| --- | --- |
| 表面表現と証拠束 | 住所文字列を直接実体へ変換しない。 |
| 展開と候補生成 | 言語展開は候補探索の前処理であり、解決ではない。 |
| 候補集合とクラスタ | 候補を一つずつ評価せず、同一実体らしい群で扱う。 |
| 評価と解決結果 | 評価が高くても保留になる場合がある。 |
| 解決とPID発行 | `resolved` でもPID発行には追加ゲートが必要。 |
| PID発行と履歴更新 | 発行後も変化、失効、merge、splitを追跡する。 |

## 7. 本文で弱めるべき点

| 原稿上の注意点 | 理由 | 修正文 |
| --- | --- | --- |
| `2^{T_t}` や `2^{X_t}` をそのまま使う | 実装上は有限集合である。 | `P_f(T_t)`, `P_f(X_t^{known})` と書く。 |
| クラスタを常に `Partitions(C)` とする | 類似性が同値関係とは限らない。 | クラスタ族、被覆、有界クラスタとして扱う。 |
| `D` を距離と呼ぶ | 対称性や三角不等式を満たさない可能性がある。 | 構造的非類似度と呼ぶ。 |
| `conditional` を形式化済みの型として扱う | Lean中核にはまだない。 | 条件付き保留として扱うか型拡張する。 |
| PIDを解決結果の自然な出力とする | PIDはより強い監査条件を必要とする。 | PID発行ゲートを別段階にする。 |

## 8. 総合評価

第7章の方向性は正しい。AMTを単発の住所正規化ではなく、証拠を保存しながら候補、クラスタ、評価、保留、PID、履歴へ進む写像連鎖として定義することは、第6章の不可能性定理とよく接続している。

特に、次の点は強く採用できる。

| 採用点 | 評価 |
| --- | --- |
| 住所解決を多段写像として扱う | AMTの中核。 |
| 解析を証拠構造化として扱う | 正規化衝突を避ける。 |
| 検索言語をアプリ表示言語から分離する | 多言語地名検索に強い。 |
| 候補生成を再現率重視にする | 候補欠落補題に整合。 |
| クラスタ評価後に保留状態を許す | 誤発行を避ける。 |
| PID発行を別ゲートにする | 安全性と監査性が上がる。 |
| 履歴更新を連鎖末尾に置く | 住所保存則、履歴グラフへ接続する。 |

修正が必要なのは、有限集合の明示、クラスタ分割の過剰仮定、`conditional` 状態の扱い、評価関数の向き、PID発行条件の明示である。

推奨判定:

| 項目 | 評価 |
| --- | --- |
| 理論的中心性 | 非常に高い。 |
| Leanとの整合 | 条件付きで高い。`conditional` は要整理。 |
| 実装との整合 | 高い。46件の関連テストが通過。 |
