# 住所写像論 日本語版 v1 第22章 追加・編集差分案

対象: 第22章「セキュリティ・悪用・ガバナンス」

本差分案は、第22章を、住所写像論全体の安全境界を定義する章として強化するための本文案である。中心方針は、住所を高リスク情報として扱い、AMT本体、AGID/AOID応用、ZK住所証明、credential、MCP/API、運用ガバナンスを混同しないことである。

## 1. 章冒頭に追加する要約

第22章の冒頭に、次を追加するとよい。

> 住所は高リスク情報である。住所は、居住、移動、配送、家族、職場、財産、避難、支援、本人確認に結びつく。したがって、住所写像論は、単に住所を解決する理論ではなく、解決してよい場合、解決を保留すべき場合、公開してよい属性、秘匿すべき属性、監査として残してよい情報を区別する理論でなければならない。

続けて、次を入れる。

> AMTは暗号プロトコルそのものではない。AMTは、安全な住所システムを作るための意味論的前提を提供する。具体的な鍵管理、ZK回路、credential発行、MCP/API、AOID同期、Polkadot anchoring、買い物Agent連携は、AGID/AOID応用論文または住所写像論IIで扱う。

## 2. 22.1に「高リスク住所情報原則」を追加する

22.1の末尾に、次を追加する。

### 原則22.1 高リスク住所情報原則

> 住所は、個人、財産、移動、配送、職場、避難、本人確認に接続する高リスク情報である。

本文案:

> 住所は、単なる地図上の点ではない。住所本文、部屋番号、配送指示、電話番号、受取人、AOID秘密鍵、credential、配送履歴、監査ログは、それぞれ異なる攻撃面を持つ。したがって、AMTではこれらを一括して「住所データ」と呼ばず、公開地理参照、私的配送情報、所有証明、監査情報、出典情報、品質情報として分けて扱う。

## 3. 22.1に資産分類表を追加する

22.1の後に、次の表を追加する。

| 資産 | 例 | 主要リスク |
|---|---|---|
| 個人住所本文 | 番地、部屋番号、建物名 | 漏えい、ストーキング、過剰開示 |
| AOID秘密情報 | 秘密鍵、所有credential、private salt | 乗っ取り、なりすまし、権限委譲悪用 |
| 配送情報 | 受取人、電話番号、置き配指示 | 配送詐欺、住居推定 |
| 監査情報 | PID発行理由、履歴root、commitment | linkability、再識別 |
| 出典情報 | 公式ソース、地図ソース、郵便ソース | 出典汚染、古いデータ、ライセンス違反 |
| 品質情報 | 内部スコア、低品質地域、再検証理由 | 濫用、差別的扱い、攻撃対象化 |
| 公開識別子 | AGID、PID、public AOID reference | 相関、追跡、replay |

本文案:

> セキュリティ設計では、何を守るかを最初に分ける必要がある。AGIDのような公開地理参照と、AOIDのような私的配送・所有情報を同じ公開面に置いてはならない。また、監査可能性のために住所本文をログへ保存する設計は、監査ログ自体を漏洩源にしてしまう。

## 4. 22.2に攻撃者モデルを追加する

22.2の冒頭または末尾に、次を追加する。

### 22.2.1 攻撃者モデル

| 攻撃者 | 目的 | 代表的な攻撃 | 対策 |
|---|---|---|---|
| 外部閲覧者 | 公開情報から個人住所を推定する | public QR、API、地図表示の相関 | public payload redaction、private fields禁止 |
| 悪意ある登録者 | 偽住所や重複AOIDを登録する | 他人住所登録、二重登録 | nullifier、credential、issuer trust、audit proof |
| 悪意ある配送者 | 配送資格や受取資格を悪用する | 配送可能性の偽装 | purpose scope、freshness、delivery eligibility |
| 悪意あるデータ提供者 | 出典を汚染する | 偽地物、古い境界、偽郵便情報 | source registry、license audit、GIS warning budget |
| 内部運用者 | ログから個人を再識別する | 生ログ閲覧、履歴相関 | log redaction、commitment監査、最小保持 |
| replay攻撃者 | 古いproofやnullifierを再利用する | challenge再利用、bundle replay | challenge、domain separation、revocation root |
| 過剰自動化システム | 低品質地域で誤発行する | UI都合の強制発行 | quality gate、unresolved、revalidation-required |

本文案:

> 第22章で扱う脅威は、単なるサイバー攻撃に限らない。住所処理では、ストーキング、配送詐欺、政治的名称の誤用、災害時の支援漏れ、低品質地域での過剰自動化、監査ログからの再識別も安全上の失敗である。

## 5. 22.2の脅威一覧を整理する

既存の箇条書きはよいが、次の表に置き換えると読みやすい。

| 脅威 | 影響 | AMT上の対策 |
|---|---|---|
| 住所本文の漏えい | 個人安全の侵害 | 最小開示、ログ赤字化、public/private分離 |
| 過剰開示 | 目的外利用 | purpose scope、属性写像、ZK住所述語 |
| 偽住所登録 | 誤配送、詐欺 | credential、issuer trust、audit proof |
| 重複登録 | 二重受取、登録濫用 | duplicate nullifier |
| 出典汚染 | 誤解決、誤発行 | source registry、license audit、source rejection |
| 履歴改ざん | 誤った同一性 | append-only lineage、correction edge |
| PID誤発行 | 永続的誤識別 | issue gate、unresolved、risk budget |
| PID乗っ取り | 所有権悪用 | AOID ownership proof、delegation policy |
| 監査ログ漏えい | 再識別 | commitment、redacted envelope、最小保持 |
| 未解決状態の無視 | 誤発行 | safety abstention |
| 低品質地域での過剰自動化 | 地域差による誤判定 | quality threshold、manual review |

## 6. 22.3を「公開可能コア分離原則」として強化する

22.3の末尾に、次を追加する。

### 原則22.3 公開可能コア分離原則

> 形式モデル、状態機械、検証スクリプト、データスキーマ、ライセンス分類、品質ゲート、エラー処理、監査エンベロープは公開可能コアに属する。一方、個人住所、秘密鍵、private salt、内部濫用対策しきい値、生監査ログは秘匿運用情報に属する。

本文案:

> オープンソース化の目的は、透明性、再現性、監査可能性を高めることである。しかし、オープンソース化は秘密情報の公開ではない。AMTでは、理論、状態機械、検証方法を公開し、個人情報、秘密鍵、private salt、配送事業者の非公開リスク信号、未公開脆弱性は公開しない。

## 7. 22.3に公開可能表を追加する

| ベンチマーク方法 | 商用API比較を透明にできる。 |
| 公開API仕様 | private fieldsを受け入れない境界を明示できる。 |

## 9. 22.5に出典ガバナンス原則を追加する

22.5の末尾に、次を追加する。

### 原則22.5 出典ガバナンス原則

> 住所解決に使う出典は、権威、文脈、ライセンス、鮮度、更新頻度、異議申し立て可能性を明示しなければならない。

本文案:

> AMTは、単一の世界的住所権威を仮定しない。国、地域、配送業者、災害状況、文化的名称、政治的名称によって、信頼すべき出典は変わる。したがって、AMTは出典を単純な正解データではなく、文脈付きの証拠として扱う。

追加表:

| ガバナンス項目 | AMT上の扱い |
|---|---|
| 出典権威 | source registryとcontextで明示する。 |
| ライセンス | redistributable、review-required、restrictedを分ける。 |
| 更新頻度 | freshness windowとrevalidation-requiredへ接続する。 |
| 異議申し立て | corrected-by、superseded-by、disputed edgeを履歴へ残す。 |
| 削除要求 | raw private data削除とpublic commitment保持を分ける。 |
| 災害時例外 | 仮想住所、避難所、支援資格、鮮度を別扱いする。 |
| 政治的名称 | claim-aware displayとsource attributionを使う。 |
| 低品質地域 | 自動発行せず、manual reviewまたはunresolvedにする。 |

## 10. 22.6を安全原則一覧として再構成する

22.6の箇条書きを、次のように整理するとよい。

1. 未解決状態ではPIDを発行しない。
2. 私的住所情報を公開地理参照に混ぜない。
3. 住所本文ではなく、必要な属性だけを公開する。
4. 品質スコアを真理として扱わない。
5. 出典、ライセンス、鮮度、文脈を記録する。
6. 履歴訂正を削除ではなく訂正エッジで扱う。
7. 監査はraw dataではなくcommitmentとreason codeを中心にする。
8. 高リスク文脈では追加確認を要求する。
9. ZK、credential、AOID、MCP/APIは応用層として分離する。
10. 検証不能な主張は断定しない。

続けて、次の一文を入れる。

> これらの原則は、住所写像論本体の安全境界である。具体的な暗号プロトコルやAPI仕様は、これらの原則を破らないように応用論文で定義する。

## 11. 反例を追加する

第22章の末尾に、次の反例節を追加すると、読者に安全境界が伝わりやすい。

### 反例22.1 オープンソース化すれば安全

> 形式モデルと実装を公開しただけでは安全にならない。private salt、AOID秘密鍵、個人住所、内部リスク信号、未公開脆弱性、ログ保持方針を誤ると、公開によって攻撃面が増える。

### 反例22.2 ZKPだけで住所真実性を保証する

> ZKPは、秘密入力を公開せずに述語を満たすことを証明する。住所の真実性は、credential issuer、AMT候補、出典鮮度、失効、監査に依存する。

### 反例22.3 監査のために全入力を保存する

> 入力住所、候補リスト、電話番号、配送指示を全て監査ログに保存すると、監査ログ自体が漏洩源になる。監査はcommitment、reason code、policy version、decision、redacted envelopeを中心にすべきである。

### 反例22.4 低品質地域で強制発行する

> 低品質地域でUXのためにPIDを強制発行すると、誤配送、誤登録、重複登録、政治的名称の誤扱い、自然地物境界の誤認につながる。

## 12. 住所写像論IIへの分離文を追加する

第22章には、次の分離文を入れるとよい。

> ZK Address Proof、ZK Residence Proof、ZK Delivery Eligibility、AOID Ownership Proof、duplicate nullifier、freshness proof、consent purpose proof、proof bundle compatibilityは、AMT本体の重要な応用である。しかし、それらはAMT本体ではなく、住所写像論IIで扱う。本体論文では、どの住所由来属性が秘匿証明の対象になり得るか、どの状態では証明やPID発行を止めるべきかを定義する。

## 13. 第23章への接続文

第22章の末尾に、次を追加すると第23章へ自然につながる。

> セキュリティ原則を定義しても、AMTの性能や品質が自動的に既存APIを上回るわけではない。次章では、商用住所検証API、地図API、郵便番号データベース、ジオコーディングAPI、Plus Codes、DID、DNS/IPアドレス、配送事業者システムと比較するためのベンチマーク方法を整理する。

## 14. 第22章の推奨構成

第22章は、次の順に整理するとよい。

1. 住所は高リスク情報である
2. 守るべき資産
3. 攻撃者モデル
4. 主な脅威
5. AMT本体が提供する意味論的安全性
6. オープンソース化できる部分
7. 公開すべきでない部分
8. 出典ガバナンス
9. セキュリティ原則
10. 反例
11. 住所写像論IIとAGID/AOID応用論文への分離
12. 第23章への接続

この構成により、第22章は単なる注意喚起ではなく、AMT本体の安全境界を定義する章になる。
