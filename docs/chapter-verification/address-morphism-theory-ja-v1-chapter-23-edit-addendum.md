# 住所写像論 日本語版 v1 第23章 追加・編集差分案

対象: 第23章「ベンチマークと比較」

本差分案は、第23章を、住所写像論の検証可能性と商用API比較の限界を明確にする章として強化するための本文案である。中心方針は、商用APIに対する勝利宣言を避け、同一データセット、同一用途、同一指標による反証可能な比較設計を書くことである。

## 1. 章冒頭に追加する要約

第23章の冒頭に、次を追加するとよい。

> ベンチマークは、AMTの優位性を宣伝するためのものではない。ベンチマークは、AMTがどの条件で住所を解決でき、どの条件で保留し、どの条件で既存サービス、公式データ、配送事業者データ、追加証拠に依存するかを明らかにするための反証可能な評価手続きである。

続けて、次を入れる。

> したがって、本章では、商用住所検証APIに全面的に勝つという主張を採用しない。Loqate、Experian、Melissa、Smarty、Google Address Validation、Nominatim/libpostalなどは、それぞれ異なるデータ、用途、国、粒度に強みを持つ。AMTの比較は、勝敗ではなく、評価軸の分解から始める。

## 2. 23.1を「比較対象と比較しないこと」に整理する

23.1の構成を、次のように変えるとよい。

### 23.1 何と比較するか

本文案:

> AMTは、商用住所検証API、地図API、郵便番号データベース、ジオコーディングAPI、Plus Codes、DID、DNS/IPアドレス、配送事業者システムと比較できる。ただし、これらは同じ問題を解いているわけではない。

次の表を追加する。

| 比較対象 | 主な強み | AMTが比較すべき点 |
|---|---|---|
| 商用住所検証API | 郵便住所正規化、配送地点、公式・商用データ | 監査性、保留、自然地理、履歴、privacy |
| 地図API | 地物検索、ジオコーディング、autocomplete | 地物候補の意味論、PID発行ゲート |
| 郵便番号DB | 郵便区域、国別ルール | 郵便番号の非単射性、部分解決 |
| Plus Codes | 座標の幾何的符号化 | 住所表記、履歴、社会的同一性との接続 |
| DID | 主体識別、credential連携 | 空間参照、居住属性、配送可能性 |
| DNS/IP | 通信先解決、ルーティング | 物流・住所ルーティングとの類比 |
| 配送事業者システム | 配送可能性、受取実績 | 非公開データへの依存と監査可能性 |

### 23.1.1 比較しないこと

本文案:

> 本章では、AMTが全ての商用APIに勝つとは主張しない。特に、国別の公式郵便データ、配送事業者の非公開delivery point data、企業向けSLA、リアルタイムautocomplete、商用ジオコーディングの深度では、既存サービスが強い場合がある。

## 3. 23.2のデータセット族を評価目的付きにする

23.2の箇条書きは採用できる。ただし、単なる列挙ではなく、何を測るかを加える。

| データセット族 | 測るもの |
|---|---|
| 都市の多階層建物 | 垂直参照、部屋番号、同一建物内の粒度。 |
| 田舎の粗い住所 | 低密度地域の候補欠落、過剰解決、unresolved。 |
| 島、港、無人島、小島 | 島名、港名、海岸、配送可能性の境界。 |
| 山地、谷、洞窟 | 自然地理名を住所的参照として扱えるか。 |
| 砂漠、湿地、氷原、氷河 | sparse natural geographyと出典不足時の保留。 |
| 川、湖、滝、海岸 | 水辺地物、橋、河川区間、岸の文脈。 |
| 遺跡、世界遺産、文化財 | 文化的地物と行政住所の分離。 |
| 旧住所と行政変更 | lineage、split、merge、旧名検索。 |
| 同一郵便番号内の複数候補 | 郵便番号だけでは非単射であること。 |
| 多言語・別名・旧名 | candidate recall、表記揺れ、誤統合。 |
| 配送不可または条件付き配送地域 | delivery eligibility、追加証拠要求。 |
| 公式データ不足地域 | verifiedへ昇格しない安全性。 |

本文案:

> 都市だけで評価すれば、AMTは自然地理や田舎での課題を見落とす。郵便住所だけで評価すれば、山、湖、川、島、砂漠、湿地、遺跡、世界遺産を扱えない。英語表記だけで評価すれば、多言語候補生成と別名処理を測れない。したがって、AMTのベンチマークは、都市型、地方型、自然地理型、文化地物型、履歴型、配送制約型を分ける必要がある。

## 4. 23.3の評価指標を定義付きにする

23.3には次の表を追加する。

| 指標 | 定義 |
|---|---|
| candidate recall@k | 正解対象が上位k候補に含まれる割合。 |
| candidate miss rate | 正解対象が候補集合に入らない割合。 |
| precision@1 | 最上位候補が正解である割合。 |
| ambiguity detection rate | 曖昧な入力をambiguousとして扱えた割合。 |
| false issue rate | 誤ったPIDまたはverified resultを発行した割合。 |
| unresolved precision | 保留すべき入力をunresolvedにできた割合。 |
| over-abstention rate | 解決可能な入力を過剰に保留した割合。 |
| cluster stability | 表記揺れ、翻訳、旧名で同じ同値類を保てた割合。 |
| false merge rate | 異なる実体を同じクラスタへ統合した割合。 |
| false split rate | 同一実体を複数クラスタへ分割した割合。 |
| lineage consistency | 旧住所、行政変更、split、mergeの履歴整合率。 |
| country quality | 国別のrecall、miss、unresolved、false issue。 |
| language quality | 言語別・表記別のrecall、誤統合、候補欠落。 |
| natural feature coverage | 自然・文化地物を候補化できる割合。 |
| vertical reference support | 階、部屋、地下、ロッカー、3D区画の区別率。 |
| audit reproducibility | 同じ証拠からPID発行判断を再現できる割合。 |
| license compliance | 出典、ライセンス、更新時点を記録できた割合。 |

本文案:

> AMTにとって、正解率だけでは不十分である。曖昧な住所に対して誤ったPIDを発行しないこと、低品質地域でverifiedを強制しないこと、出典が不足する場合にunresolvedまたはadditional-evidence-requiredへ退避することも、評価対象である。

## 5. 23.3に形式的なベンチマーク単位を追加する

23.3の後に、次を追加する。

### 23.3.1 ベンチマークケース

本文案:

> AMTのベンチマーク単位を、次の組として定義する。

```text
BenchmarkCase =
  input expression
  purpose
  country or region
  allowed source set
  gold reference object or allowed abstention
  expected granularity
  privacy constraint
```

> 解決器の出力は、少なくとも verified、partial、ambiguous、unresolved、rejected、additional-evidence-required に分類する。これにより、AMTは正解と不正解だけでなく、保留、部分解決、追加証拠要求、出典拒否を評価できる。

## 7. 23.4の商用API比較方針を補強する

現行表に加えて、次を入れる。

| 比較条件 | 固定すべき内容 |
|---|---|
| 入力集合 | 同じ住所文字列、同じ誤字、同じ言語、同じ旧名を使う。 |
| 用途 | 郵便配送、本人確認、災害支援、観光検索などを分ける。 |
| 国・地域 | 国別、都市部、田舎、島、自然地理を分ける。 |
| 出典条件 | APIが使えるデータ、AMTが使えるデータを明示する。 |
| 粒度 | 郵便番号、建物、部屋、配送地点、自然地物を分ける。 |
| privacy条件 | 住所本文を出す比較と、秘匿属性だけを出す比較を分ける。 |
| 失敗状態 | wrong answer、ambiguous、unresolved、rejectedを分ける。 |

本文案:

> 同じ入力であっても、配送用途、行政用途、観光検索、本人確認、災害支援では正解が異なる場合がある。したがって、商用API比較は、用途を固定しない総合ランキングではなく、用途別のベンチマークとして設計すべきである。

## 8. 23.5を「期待が外れた場合の書き換え規則」にする

23.5は重要なので、次のように強化する。

### 23.5 期待と失敗時の記述

本文案:

> ベンチマークで期待が外れた場合、論文は主張を隠してはならない。期待が外れた結果は、AMTの弱点ではなく、適用条件、出典不足、追加証拠要求、unresolved policyを明確にする材料である。

次の表を追加する。

| 期待が外れた結果 | 書き換え方 |
|---|---|
| 候補生成recallが低い | 当該地域では候補生成十分性が未達であり、追加ソースまたはunresolvedが必要と書く。 |
| 商用APIに配送地点で負ける | 商用APIが非公開delivery point dataを持つ範囲ではAMTは補完層と書く。 |
| 多言語展開で誤統合が出る | 多言語展開は同一性判定ではなくcandidate expansionに限ると書く。 |
| 自然地理coverageが不足する | source-bound referentとして扱い、全世界網羅を主張しない。 |
| unresolvedが多すぎる | 出典、候補生成、閾値、UI再確認の改善対象として書く。 |
| false issueが出る | PID発行ゲート、品質しきい値、追加証拠要求を強化すると書く。 |

## 9. 本章に入れるべき原則

第23章の末尾に、次の原則を追加するとよい。

### 原則23.1 同一条件比較原則

> 住所解決器を比較するときは、入力集合、用途、国、出典条件、粒度、privacy制約、評価指標を固定しなければならない。

### 原則23.2 非発行評価原則

> ベンチマークでは、正しく発行する能力だけでなく、発行すべきでないときに発行しない能力を評価しなければならない。

### 原則23.3 用途別最適性原則

> 配送、消防、行政、不動産、観光、災害支援では最適な住所解決が異なるため、単一の総合順位だけで評価してはならない。

### 原則23.4 出典境界原則

> 公式郵便データ、商用配送データ、OSS地図データ、自然地理データ、文化財データは、同じ信頼度として扱ってはならない。

### 原則23.5 反証可能性原則

> ベンチマークで期待が外れた場合、主張を隠さず、反例、適用条件、不足データ、unresolved policy、追加証拠要求として書き換えなければならない。

## 10. 避けるべき表現

第23章では、次の表現を避ける。

| 避ける文 | 理由 |
|---|---|
| AMTはLoqate、Experian、Melissa、Smartyに勝つ。 | 同一条件のライブ比較をしていない。 |
| AMTは世界中の全住所を完全に検証できる。 | 全世界gold datasetとdelivery point dataがない。 |
| AGIDは商用住所APIの代替である。 | 現時点では補完層として書く方が正確。 |
| 正解率だけで比較すれば十分である。 | false issue、unresolved、監査、privacy、licenseを見落とす。 |

代わりに、次の表現を使う。

> AMTは、商用住所検証APIを単純に置換するものではない。AMTは、曖昧性、保留、履歴、自然地理、垂直参照、出典監査、PID発行監査を評価軸として明示することで、商用APIが公開しにくい判断根拠と失敗状態を可視化する補完的な理論基盤である。

## 11. 章末に追加する結論

第23章の末尾に、次を追加するとよい。

> 本章の結論は、AMTが全ての既存サービスより優れているということではない。結論は、AMTが住所解決の評価軸を分解できるということである。商用APIは郵便住所、配送地点、公式データで強い場合がある。地図APIは地物検索とジオコーディングで強い。OSS系は監査性とコストで強い。AMTは、これらを同じ評価空間に置き、曖昧性、保留、履歴、自然地理、垂直参照、監査可能PID発行を明示する。

続けて、次を入れる。

> したがって、AMTのベンチマークは、勝敗表ではなく、条件付き能力表である。ある条件ではverifiedを返し、ある条件ではpartialを返し、ある条件ではambiguousまたはunresolvedを返す。この区別こそが、AMTを安全な住所参照理論として扱うための基礎である。

## 12. 第24章への接続文

第24章「ケーススタディ」へ接続するため、最後に次を入れるとよい。

> 次章では、本章で定義した比較軸を、具体的なケーススタディに適用する。都市の部屋、田舎の粗い住所、島、山、湖、川、砂漠、湿地、世界遺産、旧住所、避難所、秘匿配送の各例を通じて、AMTが解く部分、既存サービスに依存する部分、未解決として保留すべき部分を分けて示す。
