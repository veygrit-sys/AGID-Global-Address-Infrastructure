# 住所写像論 日本語版 v1 第11章 追加・編集差分案

対象: `docs/address-morphism-theory-ja-v1-master.md` 第11章

目的: 第11章「安全な解決とPID発行」を、検証済みのLean命題、PID衝突リスク、PID発行監査、AMN解決エンベロープに合わせて強化する。

## 1. 編集方針

第11章では、次の三段階を明確に分ける。

```text
候補表示
  ↓
解決判定
  ↓
PID発行
```

候補表示は検索結果であり、複数候補や曖昧性を含んでよい。

解決判定は、文脈の下で最もよい参照対象を選ぶ操作である。

PID発行は、長期的に監査される識別子を作る操作であり、解決判定よりさらに強い条件を要求する。

## 2. 11.1 に追加する三段階モデル

11.1の末尾に、次を追加するとよい。

| 操作 | 入力 | 出力 | 失敗時 |
| --- | --- | --- | --- |
| 候補表示 | 住所文字列、文脈、出典 | 候補集合 | 候補なし、低品質候補 |
| 解決判定 | 候補集合、クラスタ、評価関数 | `resolved`, `ambiguous`, `unresolved`, `rejected` | 非発行状態 |
| PID発行 | 解決結果、許容述語、履歴、監査条件 | PID証明書 | 発行保留 |

追加本文:

> PID発行は、検索候補を一つ選ぶ操作ではない。PIDは、住所文字列の最善推測ではなく、宣言された候補生成、クラスタリング、未解決判定、品質評価、鮮度確認、リスク評価、履歴整合性確認、監査準備を通過した参照に対してのみ発行される。

## 3. 11.2 の許容述語を検証対応へ寄せる

現在の `Admissible` は良い。次の対応表を加えると、Lean検証との接続が明確になる。

| 本文の条件 | Lean/実装上の対応 | 意味 |
| --- | --- | --- |
| `CoverageOK` | `entity ∈ candidates` | 発行対象が候補集合に含まれる。 |
| `ClusterUnique` | `ScoreSelectable` | 最良候補がしきい値以下で、第二候補と十分に離れている。 |
| `QualityOK` | `qualityThreshold <= qualityScore` | 内部品質が基準を満たす。 |
| `Fresh` | `freshnessAge <= freshnessLimit` | 出典・証拠・credentialが古すぎない。 |
| `RiskOK` | `riskScore <= riskLimit` | 衝突・誤解決・漏洩リスクが予算内。 |
| `HistoryOK` | PID lifecycle / history update | 旧住所、新住所、merge/split、失効と矛盾しない。 |
| `AuditReady` | PID audit proof | 手続きが後から検証できる。 |

追加本文:

> この許容述語は、世界の真理そのものを証明するものではない。むしろ、AMTが宣言した発行手続きにおいて、PIDを発行してもよい条件が満たされたことを示す。

## 4. 11.3 候補被覆を弱めて正確にする

候補被覆は「全世界完全列挙」ではないので、次を追加する。

> `CoverageOK` は、対象世界の完全列挙を意味しない。これは、宣言された地域、文脈、出典、言語、粒度、時刻の範囲で、候補欠落リスクが許容範囲内であるという条件である。

反例表:

| 状況 | `CoverageOK` が危険になる理由 |
| --- | --- |
| 未対応国・未対応地域 | 公式データや地図データが不足する。 |
| 建物内部住所 | 階、部屋、入口、ロッカー情報が不足する。 |
| 自然地理 | 川、湖、山、島、砂漠などの境界が不安定。 |
| 災害時住所 | 仮設住所、避難所、支援拠点が頻繁に変わる。 |
| 多言語地名 | 翻訳、旧名、略称、現地語表記が不足する。 |

## 5. 11.4 クラスタ一意性にLean命題を追加する

本文の式:

\[
E(k^\*) \leq \theta_E
\]

\[
E(k_2)-E(k^\*) \geq m
\]

は、Leanの `ScoreSelectable` と対応する。

追加本文:

> 最良クラスタが十分によいだけでは足りない。第二候補との差が小さい場合、最良クラスタは相対的に不安定である。このためAMTでは、絶対しきい値と候補間マージンを同時に要求する。

Lean対応:

```text
score_selection_requires_threshold
tied_evidence_prevents_score_selection
score_selection_conditions_are_recoverable
```

## 6. 11.5 品質、鮮度、リスクを発行不可条件として書く

現在の本文に次を追加する。

| 条件不足 | 発行不可になる理由 | Lean対応 |
| --- | --- | --- |
| 品質不足 | 出典、候補、クラスタ、履歴の信頼性が低い | `low_quality_prevents_issue` |
| 鮮度不足 | 古い住所、失効credential、古い地図に基づく危険 | `stale_freshness_prevents_issue` |
| リスク過大 | 誤配送、誤本人確認、衝突、漏洩が許容範囲外 | `high_risk_prevents_issue` |

追加本文:

> 品質、鮮度、リスクは単なる補助スコアではない。これらはPID発行の停止条件である。どれか一つでも許容範囲を外れる場合、AMTはPID発行を保留する。

## 7. 11.6 履歴整合性をPID lifecycleへ接続する

本文に次を追加する。

> `HistoryOK` は、第12章の履歴グラフと接続される。PID発行後も、住所の統合、分割、失効、再割当、建替え、行政変更が起きるため、PIDは履歴グラフ上で更新、merge、split、supersede され得る。

追加表:

| 履歴イベント | PID上の扱い |
| --- | --- |
| 住所表記変更 | 同一参照ならPID維持 |
| 行政変更 | lineageが保存されるなら継承 |
| 建物分割 | PID split候補 |
| 複数表記の統合 | PID merge候補 |
| 失効 | PID retired または superseded |
| 再開発 | 旧PIDと新PIDを履歴で接続 |

## 8. 11.7 監査可能性を最小公開にする

現在の本文に、次を追加する。

> 監査可能性は、入力住所や候補の全公開を意味しない。AMTの監査は、入力、候補集合、クラスタ、履歴更新、品質条件、発行時刻をコミットメントとして保持し、必要に応じて手続きが再確認できるようにする。

公開してよいもの:

| 情報 | 公開可否 |
| --- | --- |
| PID | 公開可能 |
| ワークフローステップ | 公開可能 |
| ポリシーバージョン | 公開可能 |
| 品質しきい値の通過結果 | 公開可能 |
| 入力住所本文 | 原則非公開 |
| 生候補 | 原則非公開 |
| 生クラスタ | 原則非公開 |
| 個人履歴 | 非公開 |
| AOID、電話番号、受取人 | 非公開 |

## 9. 11.8 PID証明書を拡張する

PID証明書の例文を次のように強化する。

```text
このPIDは、ポリシーバージョン v と評価関数バージョン e の下で、
候補生成、クラスタリング、未解決ゲート、
候補包含確認、スコア分離確認、品質しきい値確認、
鮮度確認、リスク予算確認、履歴更新、
監査コミットメント生成を通過した。

この証明書は、PIDが世界の絶対真理であることを示すものではない。
宣言された手続きと証拠範囲の下で、PID発行が許容されたことを示す。
```

## 10. 11.9 PID衝突リスクを二層に分ける

本文に次の表を追加する。

| リスク | 内容 | 対策 |
| --- | --- | --- |
| ビット列衝突 | 有限長PIDが同じ値になる | ビット長、発行量、誕生日境界、リスク予算 |
| 意味論上の衝突 | 別実体を同じ参照として発行する | 候補生成、クラスタ、未解決ゲート、履歴、品質、監査 |

追加本文:

> PIDのビット列が衝突しないことは、住所意味論上の正しさを保証しない。逆に、住所意味論上のクラスタが正しくても、有限長ハッシュPIDには数学的な衝突リスクが残る。したがって、AMTではこの二種類のリスクを分けて扱う。

実装検証として書ける内容:

| 発行量 | ビット数 | 許容リスク | 結果 |
| --- | --- | --- | --- |
| \(10^{12}\) | 128 | \(10^{-12}\) | 予算内 |
| \(10^{15}\) | 128 | \(10^{-12}\) | 予算超過 |
| \(10^{12}\) | 96 | \(10^{-12}\) | 予算超過 |

注意:

> これらは実装上のリスク予算の例であり、永遠に固定される定数ではない。発行量、用途、リスク許容度に応じて再評価する。

## 11. 直接住所PIDを禁止する節を追加する

11.9の後に、次の小節を追加するとよい。

### 11.x 住所文字列からの直接PID発行禁止

追加本文:

> AMTでは、生の住所文字列または正規化後の住所文字列から直接PIDを発行してはならない。住所観測は非単射であり、異なる実体が同じ観測を持つ場合がある。この場合、観測だけを入力とするPID関数は、異なる実体へ同じPIDを与える。

Lean対応:

```text
observation_based_pid_collides_on_same_observation
```

反例:

| 入力 | 問題 |
| --- | --- |
| `Main Street, Springfield` | 複数州・複数都市に候補がある。 |
| 同じビル名 | 別地域に同名建物がある。 |
| 旧住所 | 分割・統合後に複数現在住所へ対応し得る。 |
| 部屋番号なし住所 | 建物までは同じでも受取点が違う。 |

結論:

> PIDは文字列のハッシュではなく、AMT発行ゲートを通過した参照の識別子である。

## 12. 11.10 応用識別子との境界を明確にする

現在の方向性は正しい。次を追加するとよい。

| 層 | 扱うもの |
| --- | --- |
| AMT本体 | 候補生成、クラスタ、未解決、PID発行ゲート、履歴グラフ |
| AGID/AOID応用 | 登録、所有、配送、QR、権限委譲、買い物Agent |
| AMN応用 | 公開エンベロープ、RPID、DPID、監査コミットメント |
| ZKP応用 | 住所を秘匿した属性証明、配送可能性、居住証明 |

追加本文:

> AMT本体は、住所意味論とPID発行条件を定義する。AGID、AOID、AMN、ZK証明、配送API、買い物Agentは、その上に構築される応用層である。応用層の仕様変更があっても、AMT本体の候補、クラスタ、未解決、PID発行ゲート、履歴グラフは再利用できる。

```text

```


```text
pidCollisionRisk.test.ts
```

## 14. 本文で避けるべき表現

| 避ける表現 | 理由 | 修正文 |
| --- | --- | --- |
| PIDは絶対に衝突しない | 有限長ハッシュでは不正確 | PID衝突リスクは予算で管理する。 |
| PIDは住所の真実性を保証する | PIDは手続き通過を示す | PIDは宣言された条件下で発行許容された参照である。 |
| 候補が一つならPID発行できる | 品質、鮮度、リスクが不足し得る | 許容述語を満たす場合のみ発行できる。 |
| 住所文字列をハッシュしてPIDにする | 非単射観測で衝突する | AMTゲート通過後の参照から発行する。 |
| 監査には住所全文公開が必要 | プライバシー侵害 | コミットメントと最小公開で監査する。 |
| RPID/DPID/AOIDをAMT本体に混ぜる | 理論の境界が曖昧になる | 応用層として分離する。 |

## 16. 章末に入れるまとめ文

第11章の末尾に、次を入れるとよい。

> AMTにおけるPIDは、住所文字列の単純なハッシュではない。PIDは、候補生成、クラスタリング、未解決ゲート、候補包含、スコア分離、品質、鮮度、リスク、履歴整合性、監査準備を通過した参照に対して発行される。PIDは世界の絶対真理を保証するものではなく、宣言されたAMT手続きとリスク予算の下で発行が許容されたことを示す識別子である。この分離により、AMTは検索候補の便利さと、長期識別子の安全性を両立できる。

## 18. 最終判断

第11章は、住所写像論の実装論として非常に強い章である。修正の中心は、PIDを過大に主張しないこと、直接文字列PIDを禁止すること、有限長PIDの衝突リスクをリスク予算として扱うことである。

これらを入れれば、第11章はLean検証、実装テスト、PID監査、AMN応用層と整合する。
