# 住所写像論 日本語版 v1 第14章 検証ノート

対象: 第14章「文脈相対的最適性」

本ノートは、第14章で主張されている「住所の正しさや最適性は用途・観測者・リスク・粒度・出典範囲に依存する」という考えを、Lean形式化、GIS検証、実装テスト、反例分析に照らして検証したものである。

結論を先に述べると、第14章はかなり強く採用してよい。ただし、「絶対住所は存在しない」と言い切るのではなく、「文脈ごとの最適条件が衝突する場合、条件を隠した単一出力は同時に最適になれない」と書く必要がある。

## 1. 検証結果の要約

| 観点 | 判定 | 理由 |
|---|---:|---|
| 住所の正しさは用途に依存する | 採用 | 配送、消防、行政、不動産、自然地理、災害支援で必要情報が異なる。 |
| 文脈効用モデル | 採用 | 目的別の評価関数を置くことで数学的に扱える。 |
| 文脈衝突が普遍最適性を壊す | Leanで支持 | `strictly_better_context_blocks_universal_optimum` が対応する。 |
| 文脈衝突が絶対的住所表示を妨げる | Leanで支持 | `conflicting_context_optima_prevent_absolute_address` が対応する。 |
| 表示が違っても参照クラス/PIDを保てる | Leanで支持 | `relative_rendering_preserves_class_pid` が対応する。 |
| すべての文脈で住所は必ず異なる | 不採用 | 同じ住所表記が複数文脈で十分な場合がある。 |
| 絶対住所は一切存在しない | 不採用 | 反例がある。正しくは「衝突する文脈では単一出力が普遍最適になれない」。 |
| Address No Free Lunch | 条件付きで採用 | 用途、国、データ品質、リスクが異なると単一万能解決器は一般には成立しない。 |

第14章の安全な中心文は次である。

> 住所解決の最適性は、文脈が課す目的関数に相対的である。文脈間で最適出力が衝突する場合、文脈を入力に含まない単一解決器は、両方の文脈で同時に最適な出力を返せない。

## 3. Leanで確認できる部分

### 3.1 文脈別最適性

`formal/AMTPaperExtensions.lean` では、文脈 `Context`、解決器 `Resolver`、コスト関数 `cost : Context -> Resolver -> Nat` を用いて、文脈内最適性が定義されている。

```text
OptimalInContext cost context resolver
```

意味は、同じ文脈において、その解決器より低いコストを持つ代替解決器がない、ということである。本文の効用 `U_c` は「高いほど良い」形で書かれているが、Leanでは「低いほど良い」コストで定義されている。両者は符号を反転すれば同じ構造になる。

### 3.2 文脈衝突は普遍最適性を壊す

Lean命題:

```text
strictly_better_context_blocks_universal_optimum
```

意味:

> ある文脈で `better` が `worse` より厳密に低コストなら、`worse` はその文脈を含む二文脈で普遍最適にはなれない。

これは第14章の命題2と対応する。本文の命題は候補 `x,y` と効用 `U` で書かれているが、Leanでは解決器とコストの形で証明されている。

### 3.3 文脈衝突は絶対的住所表示を妨げる

Lean命題:

```text
conflicting_context_optima_prevent_absolute_address
```

意味:

> 配送文脈の最適表示と緊急対応文脈の最適表示が異なるなら、単一の絶対住所表示が両方に同時一致することはできない。

これは「条件なしの一つの住所文字列が常に最適」という主張を否定する。ただし、「あらゆる場合に絶対住所が存在しない」とまでは言わない。

### 3.4 表示差は参照クラス/PID差とは限らない

Lean命題:

```text
relative_rendering_preserves_class_pid
```

意味:

> 同じ参照クラスから、目的別に異なる住所表示を生成しても、その参照クラスに対応するPIDは保てる。

これは第14章で非常に重要である。配送用表示、行政用表示、災害支援用表示、ZK述語用出力が異なっても、それが同じ参照クラスから出ているなら、PIDを変える必要はない。

## 4. GISで確認できる部分とできない部分

GISは、第14章の「文脈相対性」そのものを証明する道具ではない。しかし、文脈別に必要な空間属性が異なることを検証するためには有効である。

| 文脈 | GISで検証できるもの |
|---|---|
| 配送 | 入口、道路接続、配送区域、建物付近の到達点 |
| 消防 | 進入経路、建物位置、危険区域、避難経路候補 |
| 行政 | 行政区域、管轄、境界内外 |
| 不動産 | 筆界、区画、建物 footprint、隣接関係 |
| 自然地理 | 山、湖、川、島、砂漠、湿地、アクセス点 |
| 災害支援 | 避難所、仮設拠点、浸水・危険区域、支援対象エリア |

一方で、GISだけでは次を決められない。

| GISだけでは決められないもの | 理由 |
|---|---|
| どの文脈を優先するか | 目的、契約、法制度、ユーザー同意が必要。 |
| 配送で詳細住所を出してよいか | プライバシーと同意スコープが必要。 |
| 行政表記が現在有効か | 公式出典と時刻が必要。 |
| 緊急時に開示してよい情報範囲 | 法制度、緊急権限、ポリシーが必要。 |
| 不動産境界の法的効力 | 地籍・登記・制度証拠が必要。 |

したがって、第14章では「GISが最適文脈を決める」とは書かない。正しくは「文脈別に必要な空間属性をGISで検証し、最終判断は目的関数・証拠・ポリシーで行う」である。

## 6. 第14章の主要主張ごとの判定

### 6.1 住所の正しさは用途に依存する

判定: 採用。

配送では入口、部屋番号、受取可能性が重要である。消防では進入経路、階、危険情報が重要である。行政では公式表記や管轄が重要である。不動産では筆界や登記が重要である。自然地理では地物範囲やアクセス点が重要である。

ただし、「用途が違えば必ず出力が違う」とは書かない。違う可能性があり、最適条件が衝突する場合に違う、が正しい。

### 6.2 文脈効用モデル

判定: 採用。ただし存在条件を書く。

本文では `U_c(x,s)` と書かれている。これは分かりやすいが、最適候補を定義するには、候補集合が有限である、または最大値が存在する条件が必要である。

実装論文としては、次で十分である。

```text
For a finite candidate set C_s, choose argmax_x U_c(x, s).
```

Leanに合わせるなら、コスト関数で書いてもよい。

```text
For a finite candidate set C_s, choose argmin_x K_c(x, s).
```

どちらでもよいが、本文内で「高いほど良い」か「低いほど良い」を統一する必要がある。

### 6.3 文脈相対的最適性命題

判定: Leanで支持。

現在の命題2はよい。ただし、「文脈を入力に含まない単一解決器」と明記している点が重要である。文脈を入力に含む解決器 `R(s,c)` なら、両文脈で異なる最適出力を返せる。

したがって、命題の結論は次が安全である。

> 文脈を入力に含まない単一解決器 `R(s)` は、文脈間で最適候補が衝突する場合、すべての文脈で同時に最適な出力を返せない。

### 6.4 住所相対性原理

判定: 採用。ただし「相対性」の意味を限定する。

住所相対性原理は、「何でも主観でよい」という主張ではない。正しくは、目的関数、証拠、リスク許容度、必要粒度、開示ポリシーを文脈として明示し、その文脈内で最適性を評価するという主張である。

### 6.5 Address No Free Lunch

判定: 条件付きで採用。

Address No Free Lunchは、第14章の文脈相対性を一般化した原理として有効である。ただし、一般的なNo Free Lunch定理の厳密な形式をそのまま借りるなら、仮定を丁寧に書く必要がある。

安全な表現:

> すべての国、言語、用途、データ品質、対象種別、リスク許容度で同時に最適である単一の住所解決器は、文脈間で最適条件が衝突する場合、一般には存在しない。

## 7. 反例分析

第14章には、次の反例を置くと主張が強くなる。

| 強すぎる主張 | 反例 | 修正 |
|---|---|---|
| 絶対住所は存在しない | 一戸建てでは配送、タクシー、通常案内で同じ表記が十分な場合がある。 | 衝突文脈では単一出力が普遍最適になれない。 |
| 用途が違えば必ず住所も違う | 行政と配送が同じ公式住所を使える場合がある。 | 用途ごとの最適条件が衝突するときに違う。 |
| 詳細住所が常に最良 | 国在住証明や匿名配送可能性証明では過剰開示になる。 | 詳細度も文脈で最適化する。 |
| AGIDがすべての用途に十分 | AOID、受取人、部屋番号、ロッカー、ZK述語には不足する。 | AGIDは公開参照アンカー、出力は目的別。 |
| GISが最適住所を決める | GISは空間属性を与えるが、目的や同意は決めない。 | GIS + 目的関数 + 証拠 + ポリシーで決める。 |
| 文脈相対性なら基準が不要 | 文脈内では明確な基準が必要である。 | 基準を文脈として明示する。 |

## 8. 追加すべき命題

### 命題14.1 文脈明示原理

住所解決、住所表示、住所検証、PID発行、住所証明を行うとき、少なくとも目的、時刻、管轄、必要粒度、出典範囲、リスク許容度、開示ポリシーを文脈として明示する必要がある。

### 命題14.2 文脈衝突定理

同じ入力 `s` と候補集合 `C_s` に対し、文脈 `c1` では `x` が `y` より厳密に高効用であり、文脈 `c2` では `y` が `x` より厳密に高効用であるなら、文脈を入力に含まない単一解決器 `R(s)` は両文脈で同時に最適になれない。

これは本文の命題2であり、Leanの `strictly_better_context_blocks_universal_optimum` と対応する。

### 命題14.3 表示相対性とPID不変性

同じ参照クラスから複数の文脈別住所表示を生成しても、参照クラス自体が変わらない場合、PIDは不変に保てる。

これはLeanの `relative_rendering_preserves_class_pid` と対応する。

### 命題14.4 関係変更と表示変更の分離

文脈によって住所表示が変わることと、参照対象が変わることは同じではない。前者はレンダリング差であり、後者は候補選択または関係ラベル差である。

### 命題14.5 文脈不足時の保留原理

必要な文脈が指定されていない場合、解決器は「唯一の正しい住所」を断定せず、一般検索用候補、複数出力、またはunresolvedを返すべきである。

## 9. 本文で避けるべき表現

| 避ける表現 | 推奨表現 |
|---|---|
| 絶対住所は存在しない | 衝突する文脈では、条件なしの単一住所表示は普遍最適になれない。 |
| 住所の正しさは完全に主観的である | 住所の最適性は明示された文脈内の目的関数に相対的である。 |
| 用途が違えば必ず住所が違う | 用途ごとの最適条件が衝突する場合、出力が異なり得る。 |
| AGIDが全用途の最終住所である | AGIDは公開参照アンカーであり、表示・AOID・証明は目的別に生成される。 |
| 詳細な住所ほど常に良い | 必要以上の詳細はプライバシー、同意、危険性の面で低効用になり得る。 |

## 10. 最終判定

第14章は、第13章の社会的連続性を受けて、住所写像論を実用的な意思決定理論へ進める重要章である。

採用すべき中核は次である。

1. 住所の最適性は文脈に依存する。
2. 文脈とは、目的、時刻、管轄、必要粒度、出典、リスク、開示ポリシーである。
3. 文脈間で最適条件が衝突する場合、単一の文脈非依存解決器は普遍最適になれない。
4. 表示差はPID差とは限らない。
5. Address No Free Lunchは条件付き原理として書く。
6. 「相対性」は基準の放棄ではなく、基準の明示である。

この修正を入れれば、第14章はLean検証済みの形式命題を持つ強い章になる。次の第15章「住所圧縮と住所エントロピー」へ進む前に、文脈が隠れた情報として住所圧縮に寄与することを橋渡しとして書くとよい。
