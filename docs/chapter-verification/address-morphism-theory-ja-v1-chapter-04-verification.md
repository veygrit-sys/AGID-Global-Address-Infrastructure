目的: 第4章が扱う表面住所表現を、実体、参照クラス、検索言語、表示言語、履歴、郵便番号、座標、Plus Code、PIDと分離して検証する。第4章は「住所として入力・表示されるもの」と「AMTが最終的に参照するもの」を分けるための章である。

## 3. 形式的に支えられる境界

第4章では、次のLean命題が特に重要である。

| Lean名 | 内容 | 第4章への接続 |
| --- | --- | --- |
| `normalization_collision_prevents_perfect_resolution` | 正規化が異なる対象を同じ観測へ潰す場合、完全解決器は存在しない。 | 表面表現と実体を同一視してはいけない根拠。 |
| `equivalence_class_invariant_under_renaming` | 参照を保存する改名では同値類が保存される。 | 翻訳、改名、表記変更を安全に扱う条件。 |
| `renamed_address_has_same_reference_class` | 参照保存的な改名後の住所は同じ参照クラスに属する。 | 多言語表現や旧字体、別名を同値類へ入れる条件。 |
| `functional_transition_cannot_represent_split` | 一つの旧住所が複数の新住所へ分裂する場合、単純関数では表せない。 | 旧住所を単純置換ではなく履歴グラフとして扱う根拠。 |
| `conflicting_context_optima_prevent_absolute_address` | 文脈ごとに最適表現が衝突するなら、絶対的最適住所は存在しない。 | 配送用、行政用、地図用、災害支援用の表示分離。 |
| `relative_rendering_preserves_class_pid` | 目的別レンダリングが異なっても、参照クラスPIDを保てる。 | 表示言語・用途別住所とPIDの分離。 |

これらは地理的事実そのものをLeanだけで証明するものではない。Leanが検証するのは、表面表現、正規化、改名、履歴、文脈が持つ論理的制約である。地名データや地図地物の事実性はGIS検証、出典管理、実装テストに依存する。

## 5. 主張別検証

## 5.1 CH04-C01 表面表現と実体の分離

本文の「表面住所表現は実体ではない」という主張は強く採用できる。Leanの `normalization_collision_prevents_perfect_resolution` は、正規化や表記変換によって異なる対象が同じ観測に潰れる場合、観測だけから完全解決できないことを示す。

したがって、第4章では次を明確に書くべきである。

> 表面住所表現は、実体への入口であり、実体そのものではない。PIDは表面文字列から直接発行されるのではなく、候補生成、構造距離、品質ゲート、履歴評価、未解決判定を通過した参照クラスに対して発行される。

この書き方なら、同名地名、旧住所、略称、翻訳、郵便番号、座標、Plus Codeのすべてを同じ理論内で扱える。

## 5.2 CH04-C03 省略住所の扱い

省略住所は、無効入力ではなく不完全な観測として扱うべきである。例えば、建物名、部屋番号、郵便番号、町名、国名が欠けている入力は、候補生成には使えるが、そのまま確定PIDを発行してはいけない。

実装では、弱い部分住所を検出する表示テストと、証拠不足の場合に `ambiguous` または `unresolved` へ倒すAMTテストが通っている。本文では次の方針が安全である。

> 省略住所は候補生成を開始するための観測であり、候補確定の根拠ではない。省略が解消されない場合、AMTは強制的に一つの実体を選ばず、曖昧または未解決として返す。

## 5.3 CH04-C04 検索言語と表示言語の分離

この主張は実装で強く支持される。`placeSearchLanguage.test.ts` は、検索言語ポリシーがアプリ設定や住所表示言語から独立していることを確認している。`searchQuery.test.ts` は、入力文字列からネイティブ表記、英語名、アクセント除去、タイプミス耐性、島 descriptor の展開を行うことを確認している。

第4章では、少なくとも次の四つの言語層を分けるべきである。

| 層 | 役割 | 例 |
| --- | --- | --- |
| アプリ表示言語 | UIの言語 | 日本語UI、英語UI |
| 入力表現言語 | ユーザーが入力した住所や地名の言語 | `東京`, `Tokyo`, `東京都千代田区` |
| 検索展開言語 | geocoderや地名辞書へ投げる候補言語 | native, English, romanized, accent-folded |
| 住所レンダリング言語 | 出力する住所タブや配送ラベルの言語 | 国内表示、国際英語表示 |

この分離により、ユーザーが日本語UIを使っていても、英語、現地語、旧称、ローマ字、アクセントなし表記で検索できる。

## 5.4 CH04-C05 多言語展開の限界

多言語展開は検索能力を上げるが、同時に衝突も増やす。例えば、別々の地名が同じローマ字、同じ英語訳、同じ略称、同じアクセント除去後文字列になる場合がある。

Leanの正規化衝突定理は、この危険を形式的に支えている。したがって、本文では「多言語化すれば完全解決できる」と書かず、次のように限定する。

> 多言語展開は候補生成の再現率を高めるために用いる。ただし、展開後の候補は構造距離、行政階層、地理距離、出典品質、履歴、用途文脈によって再評価される。展開文字列が一致することは、同一実体であることの十分条件ではない。

## 5.5 CH04-C06 参照保存的な翻訳・改名

Lean拡張では、参照保存的な改名で同値類が保たれることが確認されている。この結果は、第4章の多言語表現や旧字体、別名、英語表示に重要である。

ただし、参照保存性は条件である。翻訳したから同じ住所になるのではなく、同じ参照対象を保つ翻訳であることが必要である。本文では次の表現が安全である。

> 表記変換、翻訳、改名、ローマ字化は、参照を保存する場合に限り、同じ住所同値類に属する。参照保存性が確認できない変換は、候補拡張として扱い、確定同一性としては扱わない。

## 5.6 CH04-C07 旧住所と履歴表現

旧住所は、単純に現在住所へ置換できるとは限らない。行政変更、区画整理、建物建替え、住居表示変更、道路新設、分筆、合筆により、一つの旧住所が複数の新住所へ分かれることも、その逆もある。

`functional_transition_cannot_represent_split` は、分裂を単純関数で表せないことを支える。第4章では、旧住所を第12章のAddress Lineageへ渡す表面表現として扱うべきである。

> 旧住所は、現在住所への単純置換表ではなく、履歴グラフ上の節点または辺として扱う。履歴証拠が不足する場合、AMTは旧住所を無理に現在住所へ変換せず、未解決または複数候補として保持する。

## 5.7 CH04-C08 郵便番号、座標、Plus Code、PID

郵便番号、座標、Plus Codeは強い証拠になり得るが、それぞれ限界を持つ。郵便番号は地域、配送経路、私書箱、建物群を表す場合がある。座標やPlus Codeは地理的位置を表すが、部屋、階、入口、受取権限、行政表記、配送手順を必ずしも表さない。

PIDは、これらの表面コードとは異なる。PIDは入力コードではなく、AMTの発行ゲートを通った参照クラスに与えられる永続識別子である。

| 表現 | 強み | 限界 | 第4章での扱い |
| --- | --- | --- | --- |
| 郵便番号 | 郵便・配送候補を強く絞れる | 一意住所とは限らない | 候補強化証拠 |
| 座標 | 地理的位置を直接表す | 垂直、権限、社会的対象を失う | 地理証拠 |
| Plus Code | 住所未整備地域で有効 | 住所制度や配送手順を表さない | 補助地理コード |
| PID | 参照クラスを安定識別する | 発行前の入力表現ではない | AMTの出力 |
| AGID/AOID | 応用層の識別子 | AMT本体とは分ける | 別論文または応用章 |

## 5.8 CH04-C09 混合表現

現実の入力は、郵便番号、旧住所、建物名、会社名、座標、地物名、自然言語説明が混ざる。第4章の混合表現の扱いは妥当である。ただし、本文では「混ぜてよい」ではなく「証拠へ分解する」と書くべきである。

推奨するモデル:

\[
m = (postal, text, geocode, building, natural, history, userContext)
\]

ここで、各成分は別々の証拠として評価される。成分同士が一致すれば候補を強化し、矛盾すれば `ambiguous` または `unresolved` へ倒す。

## 6. 弱めるべき表現

| 危険な表現 | 安全な表現 |
| --- | --- |
| 正規化後の住所が同じなら同じ実体である | 正規化後の一致は候補強化証拠であり、同一性の十分条件ではない。 |
| 英語訳できれば同じ住所である | 参照保存的な翻訳である場合に限り同じ同値類へ入る。 |
| 郵便番号で住所を特定できる | 郵便番号は候補を強く絞るが、一意の配送先を必ず表すとは限らない。 |
| 座標があれば住所は不要である | 座標は位置証拠であり、行政、言語、履歴、配送、権限を代替しない。 |
| Plus CodeはPIDである | Plus Codeは地理コード、PIDは参照クラス識別子である。 |
| アプリ言語を検索言語にすればよい | 検索言語は入力文字列と地名ソースから独立に推定する。 |
| 旧住所は新住所へ変換できる | 旧住所は履歴グラフで扱い、分裂・統合・不明を許す。 |

## 7. 最終判定

第4章は、AMTの実装可能性を支える重要章である。住所を文字列処理として扱うのではなく、表面表現から観測、候補集合、参照クラスへ進むという流れを明確にできる。

採用判断:

1. 表面表現と実体の分離は、強く採用する。
2. 省略住所を不完全観測として扱う方針は、強く採用する。
3. 検索言語、入力言語、表示言語、レンダリング言語の分離は、強く採用する。
4. 多言語展開は再現率改善策として採用し、同一性の十分条件とはしない。
5. 参照保存的な翻訳・改名では同値類が保たれると書ける。
6. 旧住所は単純関数ではなく履歴グラフで扱う。
7. 郵便番号、座標、Plus Code、PID、AGID/AOIDを明確に分離する。
8. 混合表現は証拠ベクトルへ分解し、矛盾時は曖昧または未解決へ倒す。

この整理により、第4章は「住所表記の多様性」を説明する章から、「表面表現を安全にAMTの参照モデルへ接続する章」へ強化できる。
