作成日: 2026-06-06

目的: 第8章で述べる候補生成、出典分類、出典メタデータ、多言語・別名展開、自然地理候補、履歴候補、候補被覆証拠、失敗モードが、Lean形式化、GIS検証、住所検証エンジン、自然地理表示、PID発行監査と整合するかを確認する。

## 1. 第8章の位置づけ

第8章は、AMT写像連鎖の中で「探索空間を作る」章である。

第6章の不可能性定理と第7章の写像連鎖から、次のことが分かる。

```text
候補集合に真の対象がない
  -> 構造比較でも回復できない
  -> クラスタリングでも回復できない
  -> 評価関数でも回復できない
  -> PIDを安全に発行できない
```

したがって、第8章の中心命題は「候補生成の再現率がAMT全体の上限を決める」である。ただし、候補を無制限に増やせば安全になるわけではない。候補数が増えすぎると、計算量、曖昧性、誤統合、攻撃面、監査負荷が増える。

第8章で重要なのは、次の分離である。

| 分離 | 意味 |
| --- | --- |
| 候補生成 | 可能性のある対象を広く集める。 |
| 出典検証 | 候補をどの程度信用できるかを評価する。 |
| 候補表示 | 不確実な候補もユーザーや内部処理へ示せる。 |
| 検証済み主張 | 出典と条件が十分な場合だけ成立する。 |
| PID発行 | 候補、評価、品質、鮮度、リスク、監査を通った場合だけ行う。 |

この分離により、自然地理、島、砂漠、湖、川、山、遺跡、多言語地名の検索能力を高めながら、弱い出典をそのまま永続識別子へ固定する危険を避けられる。

## 5. 主張別検証

### 5.1 CH08-C01 候補生成の再現率原則

本文の「真の対象を早く捨てない」という主張は正しい。Leanの `missing_entity_refutes_candidate_completeness` は、候補集合から対象が欠落している場合、候補完全性を主張できないことを示している。

これは自然地理や疎地域で特に重要である。山、川、湖、島、砂漠、湿地、氷原、遺跡、世界遺産、海域、港、岸、登山口、洞窟入口のような対象は、通常の郵便住所データだけでは候補に入らない場合がある。

したがって第8章では、候補生成を次のように書くとよい。

```text
Gamma_{c,t}(B)
  = union_i Adapter_i(B, c, t)
```

ここで `Adapter_i` は公式郵便、行政、地図、建物、自然地理、履歴、配送履歴、利用者補助情報などの出典アダプタである。

### 5.2 CH08-C02 候補欠落とPID非発行

Leanの `missing_candidate_prevents_issue` は、第8章に直接使える重要補題である。

意味は次の通りである。

```text
対象 x が候補集合 C に含まれない
  -> x について IssueAdmissible は成立しない
  -> PIDを安全に発行できない
```

これにより、候補生成は単なる検索UIではなく、PID発行の前提条件であることが明確になる。

本文では次を明記すべきである。

> 候補生成の失敗は後段の評価関数では回復できない。候補に含まれていない対象については、評価値が計算されず、クラスタにも入らず、PID発行条件を満たすこともできない。

### 5.3 CH08-C03 出典分類と用途別信頼

第8章の出典分類表は妥当である。ただし、より強くするには「出典種別」と「検証に使える文脈」を分ける必要がある。

| 出典 | 候補生成 | 郵便検証 | 地理検証 | 自然地理 | PID発行 |
| --- | --- | --- | --- | --- | --- |
| 公式郵便データ | 強い | 強い | 限定的 | 弱い | 郵便文脈で強い |
| 行政データ | 強い | 中 | 強い | 中 | 管轄文脈で強い |
| 地図データ | 強い | 中または弱 | 強い | 強い | 単独では要注意 |
| 建物データ | 中 | 中 | 強い | 弱い | 建物内部文脈で重要 |
| 自然地理データ | 強い | 弱い | 強い | 強い | 配送可能性とは別判定 |
| 歴史データ | 強い | 弱い | 中 | 中 | 履歴接続に必要 |
| 配送履歴 | 中 | 中 | 中 | 中 | 到達可能性で強いが偏りに注意 |
| 利用者補助情報 | 中 | 弱い | 弱い | 弱い | 単独発行不可 |

この表は、「どの出典も常に正しいとは仮定しない」という本文と整合する。

### 5.4 CH08-C04 未知・拒否ソースの非昇格

Leanの `SourceValidation` は、出典検証状態の最小モデルとして有効である。

```text
SourceValidation = accepted | unknown | rejected
```

`SourceVerified` は `accepted` のみを検証済みとみなす。Leanでは、`unknown_source_prevents_verified_claim` と `rejected_source_prevents_verified_claim` が通っている。

したがって、本文には次を追加するとよい。

> 出典は候補生成には利用できても、検証済み主張に利用できるとは限らない。未知ソース、未監査ソース、拒否ソース、失効ソースは、候補を作る補助には使えても、単独で検証済み住所、配送可能性、PID発行を支えてはならない。

### 5.5 CH08-C05 公式郵便データの強みと限界

実装テストでは、JPのzipcloud、FRのAPI Adresse、libaddressinputのような高信頼ソースが候補や検証スコアを強化することを確認した。

一方で、公式郵便データは次の対象に弱い場合がある。

| 対象 | 公式郵便データの限界 |
| --- | --- |
| 山、湖、川、砂漠、海域 | 郵便住所ではない。 |
| 島、岩礁、環礁、氷原 | 郵便番号や配送区域がない場合がある。 |
| 建物内部、入口、階、部屋 | 国や地域により公式データが不足する。 |
| 旧住所、歴史名 | 現行郵便データでは消えている場合がある。 |
| 仮想住所、災害時住所 | 公式制度に未登録の場合がある。 |

したがって、公式郵便データは「郵便住所文脈で強い」と書くべきであり、「すべての住所実体の真理源」とは書かない方がよい。

### 5.6 CH08-C06 弱い郵便ソースと候補専用モード

`addressVerificationEngine.test.ts` では、弱い郵便候補が高い confidence を持っていても、配送可能性や住所検証済み状態へ自動昇格しないことを確認している。

これは第8章の出典政策にとって重要である。

```text
weak postal evidence
  -> candidate / partial
  -> collect stronger reference
  -> only then verified
```

本文では、弱い郵便ソースを完全に捨てるのではなく、「候補生成には使うが、検証済み主張には使わない」と整理するとよい。

### 5.7 CH08-C07 no-postal地域とgeo verified

`addressCoveragePolicy.test.ts` と `addressVerificationEngine.test.ts` では、郵便番号を使わない地域について、強い公式地理データがある場合に `geo-verified` として扱えることを確認している。

重要なのは、郵便番号がないことを「住所が弱い」と決めつけないことである。

| 地域状態 | 推奨モード |
| --- | --- |
| 郵便APIが強い | `strong-postal` |
| 郵便形式だけ強い | `format-and-candidates` |
| 郵便番号なし、公式地理が強い | `geo-verified` |
| 郵便番号なし、地理ソースも弱い | `manual-required` |
| 自然地理中心 | `geo-verified` または `reverify` |

この分類は、世界全体の住所検証エンジンを作るうえで重要である。

### 5.8 CH08-C08 多言語・別名展開

`placeSearchLanguage.test.ts` と `searchQuery.test.ts` は、第8章8.4を強く支持している。

確認済みの実装挙動:

| 機能 | 確認内容 |
| --- | --- |
| アプリ言語からの独立 | 検索言語は `app-language` と `address-language` から独立。 |
| 文字体系ヒント | 漢字、かな、ハングル、キリル文字、アラビア文字、デーヴァナーガリー、タイ文字、ギリシャ文字を検出。 |
| 別名展開 | 東京、Mexico City、Bogota、Sao Paulo、Kolkataなどを展開。 |
| 誤字耐性 | `Tokio`, `Mexcio City`, `sngapore airprot` などを補正。 |
| 島名展開 | `Bali Island`, `Ile de Re`, `Isla de Pascua`, `沖縄島` を島候補へ展開。 |

ただし、本文がすでに述べている通り、別名展開は独立証拠を増やすものではない。同じ出典から派生した別名を複数持っていても、評価時には出典相関を考慮すべきである。

### 5.9 CH08-C09 自然地理候補

`naturalAddress.test.ts`, `mapFeatureAddress.test.ts`, `addressTabQuality.test.ts`, `addressMorphismSources.test.ts` により、自然地理候補の扱いは実装で支持されている。

確認済みの対象:

| 種別 | 実装で確認した扱い |
| --- | --- |
| 道路 | 道路ラベルを建物名として誤扱いしない。 |
| 橋 | 道路文脈とPOI文脈の両方で表示可能。 |
| 山 | 座標、標高、自然地物名で表示可能。 |
| 川、滝 | 水文文脈として表示可能。 |
| 湖、池、貯水池 | inland waterとして表示可能。 |
| 島、環礁、群島、キー | island environmentとして扱える。 |
| 砂漠、荒野、塩湖、氷原 | sparse naturalとして再検証候補にできる。 |
| 遺跡、世界遺産 | POI/landscape文脈として扱える。 |
| 海域、海底地物 | marine addressとして表示可能。 |

本文の「中心点だけでは不十分」という主張は正しい。線状地物、面状地物、立体地物では、候補として「対象そのもの」だけではなく、入口、岸、港、橋、登山口、管理施設、観測点、近傍施設を生成する必要がある。

### 5.10 CH08-C10 候補被覆証拠

本文の `CoverageEvidence(s,c,t,C,Q)` は適切である。ただし、これは「世界中のすべての候補が含まれる」という絶対完全性ではない。

より正確には、次を記録する監査証拠である。

| 記録対象 | 内容 |
| --- | --- |
| 入力 | 元の文字列、正規化前の表現。 |
| 文脈 | 目的、国、配送、行政、自然地理など。 |
| 時刻 | 参照データの時刻、検索時刻。 |
| 出典 | 公式、OSS、地図、自然地理、履歴、利用者補助情報。 |
| 範囲 | 地理範囲、行政範囲、検索半径。 |
| 言語展開 | 使用した言語、別名、ローマ字、旧名。 |
| 制限 | 件数上限、品質下限、ライセンス制約。 |
| 除外理由 | 候補から落とした理由。 |

GIS Lean証明書は、現在のGIS検証がエラー0であり、登録ソース数の下限を満たすことを確認している。ただし、これは世界中の自然地理候補が完全であることを証明するものではない。

### 5.11 CH08-C11 複数候補と保留

Leanの `multiple_candidates_prevent_zero_residual` と `nonzero_residual_candidates_force_ambiguity` は、第8章8.8の失敗モードと接続する。

候補生成により複数の候補が残ること自体は失敗ではない。むしろ、候補を捨てずに残した結果である。しかし、複数候補の差が十分でない場合は、強制解決ではなく `ambiguous` または `unresolved` とする必要がある。

本文では次を明記するとよい。

> 候補生成の目的は候補を一つに減らすことではない。候補生成の目的は、後段が安全に比較できる候補集合を作ることである。複数候補が残る場合、それは評価、クラスタリング、追加証拠、利用者確認、再検証へ送られる。

### 5.12 CH08-C12 出典品質と内部スコア

`addressTabQuality.test.ts` では、都市、田舎、島、山地、砂漠、湖、水域、極地、疎自然地理を内部的に分類し、低品質表示を非表示または再検証対象にする挙動を確認している。

これはユーザーへスコアを表示するためではなく、内部判定のためである。

| 内部判定 | 用途 |
| --- | --- |
| `show` | 十分な品質の表示。 |
| `reverify` | 表示はするが再検証対象。 |
| `hide` | 明らかに未解決または意味のない表示を隠す。 |
| `canSkipSecondVerification` | 安定した都市住所などで重複検証を省略可能。 |

Leanの `low_quality_prevents_issue` は、品質不足の場合にPID発行条件を満たせないことを支える。したがって第8章では、品質スコアを「ユーザー表示用」ではなく「内部安全ゲート」として書くのがよい。

## 6. 第8章で弱めるべき点

| 注意点 | 理由 | 修正文 |
| --- | --- | --- |
| 「候補生成は完全である」と書く | 世界全体の完全候補生成は検証不能。 | 宣言された出典と範囲で監査可能と書く。 |
| 公式郵便データを万能と扱う | 自然地理、建物内部、旧住所に弱い。 | 郵便文脈で強いと書く。 |
| 地図データを公式検証と同一視する | 地図は強力だが権威性が異なる。 | 地理候補・自然地理では強いが、郵便検証とは分ける。 |
| 多言語別名を独立証拠として数える | 同一出典由来の別名は相関している。 | 展開候補と独立出典を分ける。 |
| 郵便番号なしを低品質とみなす | no-postal地域が存在する。 | geo verifiedまたはmanual-requiredで扱う。 |
| 自然地理の中心点だけを住所化する | 線状・面状・立体地物では不十分。 | 岸、入口、港、登山口、管理施設も候補化する。 |
| 候補表示をPID発行と結びつける | 候補は不確実でも表示可能。 | PID発行は別ゲートにする。 |

## 7. 追加すべき命題

### 命題 8.1 候補欠落非回復命題

候補集合に真の対象が含まれていない場合、後段の構造比較、クラスタリング、評価関数、PID発行ゲートは、その対象を安全に発行できない。

解説:

> この命題はLeanの `missing_candidate_prevents_issue` と対応する。候補生成の品質はAMT全体の上限である。

### 命題 8.2 出典非昇格命題

未知、拒否、失効、または文脈外の出典から生成された候補は、追加条件なしに検証済み住所主張またはPID発行根拠へ昇格してはならない。

解説:

> この命題はLeanの `unknown_source_prevents_verified_claim` と `rejected_source_prevents_verified_claim` に対応する。候補生成と検証済み主張を分離するための命題である。

### 命題 8.3 多言語展開相関命題

同一出典から生成された複数の別名、翻訳、ローマ字、略称は、候補再現率を高めるが、独立証拠数として単純加算してはならない。

解説:

> これは実装テストで検索展開の有効性が確認されている一方、評価関数で出典相関を扱う必要があることを示す。

### 命題 8.4 no-postal非劣化命題

郵便番号がないことは、それだけで住所品質が低いことを意味しない。強い地理・行政・建物・配送証拠があれば、郵便番号なしでも地理的に検証済みの住所表示または候補を構成できる。

解説:

> no-postal国や自然地理住所を、通常の郵便住所と異なる検証モードで扱うための命題である。

## 8. 総合評価

第8章の方向性は正しい。候補生成を検索ではなく証拠収集として扱い、出典分類、メタデータ、多言語展開、自然地理、履歴、候補被覆証拠、失敗モードを分けている点は、AMT全体の安全性に直結する。

特に、次の点は強く採用できる。

| 採用点 | 評価 |
| --- | --- |
| 候補生成では再現率を重視する | AMTの安全上限を決める。 |
| 出典を常に正しいと仮定しない | 現実の住所制度に合う。 |
| 出典メタデータを評価、品質、PID、監査へ渡す | 実装可能性が高い。 |
| 多言語検索をアプリ言語から分離する | 世界規模の地名検索に必要。 |
| 自然地理候補を点・線・面・立体で分ける | 山、川、湖、島、砂漠などに対応できる。 |
| 履歴候補を現在値へ単純変換しない | 住所保存則と整合する。 |
| 候補被覆証拠を絶対完全性ではなく監査可能性とする | 過剰主張を避けられる。 |
| 失敗モードをunresolved/ambiguousへ送る | 誤解決を避ける。 |

修正が必要なのは、候補生成と検証済み主張の分離、未知・拒否ソースの非昇格、郵便文脈と自然地理文脈の区別、多言語別名の相関、品質スコアの内部化である。
