# 住所写像論 日本語版 v1 第7章 追加・編集差分案

作成日: 2026-06-06

対象: `docs/address-morphism-theory-ja-v1-master.md` 第7章

目的: 第7章「AMT写像連鎖」を、検証済みの数理モデルと実装に合わせて強化するための差し込み文、置換文、可換図式、定義、注意点をまとめる。

## 1. 編集方針

第7章は、AMTの処理パイプラインを示す章である。ここでは「住所を正規化して正解を返す」ではなく、「表面表現を証拠束へ変換し、候補、クラスタ、評価、保留、PID、履歴へ進める」と書く。

冒頭に、次を追加するとよい。

> 第6章の不可能性定理により、住所解決を単一の逆写像として扱うことは安全ではない。AMTでは、住所解決を、証拠を構造化し、候補を広げ、候補群を比較し、必要なら保留し、十分な条件を満たす場合にだけPIDを発行する写像連鎖として扱う。

## 2. 7.1 直後に入れる可換図式

7.1の現行のテキスト図式の後に、次の図式を追加する。

```text
S_t
  -- pi_{c,t} -->
B_{c,t}
  -- epsilon_{c,t} -->
E_{c,t}^{exp}
  -- Gamma_{c,t} -->
C_{c,t}
  -- D_{c,t}, Pi_{delta,c,t} -->
K_{c,t}
  -- Eval_{c,t} -->
R_{c,t}
  -- IssueGate_{c,t} -->
PID or NonIssue
  -- Update -->
H_{t+1}
```

記号表:

| 記号 | 意味 |
| --- | --- |
| \(S_t\) | 表面表現集合 |
| \(B_{c,t}\) | 解析された証拠束 |
| \(E_{c,t}^{exp}\) | 展開済み証拠束 |
| \(C_{c,t}\) | 有限候補集合 |
| \(K_{c,t}\) | クラスタ族 |
| \(R_{c,t}\) | 解決結果 |
| `IssueGate` | PID発行可否のゲート |
| \(H_{t+1}\) | 更新後の履歴状態 |

狙い:

候補返却、解決、PID発行、履歴更新を別ノードにする。これにより「候補を出す」ことと「PIDを発行する」ことの危険度差が明確になる。

## 3. 7.2 解析写像の補強

現行の

```text
pi_t : S_t -> T_t
```

は単純で分かりやすいが、実務上は解析結果が複数の証拠からなる。次のように補強するとよい。

### 追加定義 7.1 証拠束

住所表面表現 \(s\in S_t\) から得られる解析結果を、単一トークンではなく証拠束として扱う。

```text
B_{c,t}(s) =
  {
    raw text,
    normalized tokens,
    language hints,
    postal hints,
    administrative hints,
    building hints,
    natural feature hints,
    coordinate hints,
    historical hints,
    context hints,
    source traces
  }
```

解析写像は次のように置く。

```text
pi_{c,t}: S_t -> B_{c,t}
```

または有限トークン集合として、

```text
pi_{c,t}: S_t -> P_f(T_t)
```

と書く。

### 追加本文

> 解析は解決ではない。解析の目的は、入力を一つの標準文字列へ潰すことではなく、後段で必要になる証拠を失わずに構造化することである。特に、旧住所、新住所、自然地理名、建物名、階、入口、部屋番号、言語差、出典は、正規化で消してはならない。

## 4. 7.3 展開写像の補強

現行の

```text
epsilon_{c,t}: T_t -> 2^{T_t}
```

を、有限の展開済み証拠束として書く。

```text
epsilon_{c,t}: B_{c,t} -> E_{c,t}^{exp}
```

ここで \(E_{c,t}^{exp}\) は、別名、旧名、新名、現地語、英語名、ローマ字、略称、誤字候補、自然地理名、行政後継名、地図ラベルを、出典と変換規則つきで保持する。

### 追加本文

> 展開写像は検索能力を上げるための写像であり、同一性を確定する写像ではない。展開された候補語には、どの規則で生成されたか、どの言語に属するか、どの出典に由来するかを付与する。

さらに、次を入れるとユーザー方針と一致する。

> 地名検索の言語展開は、アプリ表示言語および住所表示言語から分離される。アプリが日本語表示であっても、入力地名がアラビア語、キリル文字、ローマ字、現地語、歴史名、観光名であれば、それらを検索用証拠として展開する。

## 5. 7.4 候補生成写像の修正

現行の

```text
Gamma_{c,t}: 2^{T_t} -> 2^{X_t}
```

を、実装可能性を考慮して次のように修正する。

```text
Gamma_{c,t}: E_{c,t}^{exp} -> P_f(X_t^{known})
```

ここで \(P_f\) は有限集合、\(X_t^{known}\) はAMTが時刻 \(t\) に扱える既知実体集合である。

### 追加本文

> 候補生成は、真の対象を一意に決定する段階ではない。候補生成は、後段の構造比較、クラスタリング、評価、保留判定に渡す探索空間を作る段階である。候補欠落が起きると、後段の評価関数は真の対象を回復できない。したがって、候補生成では再現率を重視する。ただし、候補を無制限に広げると計算量、曖昧性、攻撃面が増えるため、出典、地理範囲、文脈、品質により制御する。

## 6. 7.5 構造比較の補強

現行の \(D_{c,t}\) の説明に、次を追加する。

> \(D_{c,t}\) は通常の距離とは限らない。文脈によって、AからBへの非類似度とBからAへの非類似度が異なることがある。また、三角不等式を満たすとは限らない。したがって、本論文ではこれを距離ではなく構造的非類似度と呼ぶ。

クラスタリングで対称値が必要な場合の定義として、次を追加する。

```text
Dbar_{c,t}(x,y) = max(D_{c,t}(x,y), D_{c,t}(y,x))
```

または

```text
Dbar_{c,t}(x,y) = (D_{c,t}(x,y) + D_{c,t}(y,x)) / 2
```

ただし、採用する対称化規則は実装ポリシーとして明示する。

## 7. 7.6 クラスタリングの修正

現行の

```text
Pi_{delta,c,t}(C) in Partitions(C)
```

は、類似関係が同値関係になる場合にはよい。しかし、実務上の閾値クラスタは必ずしも同値関係ではない。したがって、次のように修正する。

```text
Pi_{delta,c,t}: P_f(X_t^{known}) -> ClusterFamily_{c,t}
```

### 追加定義 7.2 クラスタ族

クラスタ族 \(K_{c,t}\) は、候補集合 \(C_{c,t}\) の部分集合からなる有限族である。

```text
K_{c,t} = {K_1, K_2, ..., K_n}
where each K_i subset C_{c,t}
```

クラスタ族は、用途に応じて分割、被覆、有界クラスタ族として実装される。

### 追加本文

> しきい値で近い候補を連結するだけでは、AはBに近く、BはCに近いが、AはCに遠いという連鎖により過統合が起きる。AMTのクラスタリングは、単なる連結成分ではなく、有界性、代表点、内部非類似度、文脈、出典衝突を考慮する。

## 8. 7.7 評価関数の補強

評価関数について、次の表を入れるとよい。

| 種類 | 向き | 意味 |
| --- | --- | --- |
| エネルギー \(E_{c,t}\) | 低いほど良い | 不一致、リスク、品質不足、文脈不適合のコスト |
| 支持度 \(S_{c,t}\) | 高いほど良い | 出典、履歴、構造一致、配送実績などの支持 |
| 確信度 \(Q_{c,t}\) | 高いほど良い | 最良候補が十分強いかを表す統合値 |
| マージン \(M_{c,t}\) | 高いほど良い | 二番手との差 |

追加本文:

> 評価関数は真理そのものではない。評価関数は、現時点の観測、候補、履歴、品質、鮮度、リスクのもとで、解決してよいか、曖昧として保留すべきか、未解決にすべきか、棄却すべきかを判断する規則である。

## 9. 7.8 解決結果型の修正

現行本文には `conditional` が含まれている。これは有用だが、Lean中核の形式化ではまだ独立状態として定義されていない。次のように扱うとよい。

### 修正案

第7章では、解決結果型を次の四状態にする。

```text
R(X_t) =
  resolved(x)
  ambiguous
  unresolved
  rejected
```

そのうえで、条件付き解決は保留状態のメタデータとして扱う。

```text
unresolved(reason = "room-number-required")
ambiguous(reason = "user-must-select-building")
rejected(reason = "source-revoked")
```

### 追加本文

> `conditional` は、独立した解決状態としてではなく、追加条件を持つ保留状態として扱うことができる。たとえば、「部屋番号が追加されれば配送可能」「公式データ更新後に再検証」「ユーザーが候補建物を選べば確定」は、条件付き未解決または条件付き曖昧状態として記録される。

## 10. 7.9 PID発行ゲートの明示

PID発行または非発行の段落に、次のゲート表を追加する。

| ゲート | 発行条件 |
| --- | --- |
| 候補所属 | 発行対象が候補集合に含まれる。 |
| クラスタ一意性 | 最良クラスタが文脈上十分に明確である。 |
| 評価閾値 | エネルギーまたは支持度が閾値を満たす。 |
| マージン | 二番手との距離が十分である。 |
| 品質 | 地域、言語、自然地理、出典の品質が十分である。 |
| 鮮度 | 出典と履歴が古すぎない。 |
| リスク | PID衝突、重複登録、攻撃面が許容範囲内である。 |
| 監査 | 候補生成、クラスタ、未解決ゲート、履歴更新が監査可能である。 |

追加本文:

> PIDは、候補表示や通常の解決結果より強い意味を持つ。候補表示は探索支援であり、解決結果は文脈上の参照判定である。PID発行は監査可能な永続参照の作成である。したがって、PID発行は別ゲートとして扱う。

## 11. 7.10 履歴更新の補強

履歴更新の段落に、次を追加する。

> 履歴更新は単なるログではない。履歴は、旧住所、新住所、行政変更、分割、統合、再開発、仮想住所、失効、再割当、PID merge、PID split を表す参照グラフである。したがって、履歴更新は、現在値の上書きではなく、監査可能なイベント追加として扱う。

第12章へ送る文:

> 履歴グラフの詳細な公理、保存則、merge/splitの正当性、PID継承は第12章で扱う。

## 12. 追加すべき命題

第7章には、次の命題を入れると章が引き締まる。

### 命題 7.1 写像連鎖分離原則

解析、展開、候補生成、評価、PID発行は互いに異なる危険度を持つため、同一の関数として実装してはならない。

解説:

> 特に、候補生成や評価の結果をそのままPID発行と同一視すると、候補欠落、正規化衝突、文脈衝突、低品質データが永続参照へ固定される危険がある。

### 命題 7.2 候補表示とPID発行の非同値性

候補をユーザーに提示できることは、PIDを発行できることを意味しない。

解説:

> 候補提示は不確実性を許す。PID発行は長期参照を作るため、候補所属、評価、品質、鮮度、リスク、履歴、監査の条件を必要とする。

### 命題 7.3 保留保存原則

解決器が十分な証拠を持たない場合、誤った `resolved` を返すより、`ambiguous`, `unresolved`, `rejected` を返す方が安全である。

解説:

> 第6章の不可能性定理により、保留状態は失敗処理ではなく安全構造である。

## 13. 本文で避けるべき表現

| 避ける表現 | 理由 | 修正文 |
| --- | --- | --- |
| 解析で住所を正規化する | 解析と正規化が混ざる。 | 解析で証拠束を作る。 |
| 展開で正しい住所を得る | 展開は候補を増やすだけ。 | 展開で検索再現率を高める。 |
| 候補集合から最良候補を選べばよい | クラスタ、保留、品質、リスクが必要。 | 候補集合をクラスタ化し、評価と保留判定を行う。 |
| クラスタは常に分割である | 類似性が同値関係とは限らない。 | クラスタ族として扱う。 |
| 評価関数が正解を決める | 評価は選択規則であり真理ではない。 | 評価は発行可能性と保留可能性を判断する。 |
| 解決できたらPIDを発行する | PIDは別ゲートが必要。 | 解決後にPID発行ゲートを通す。 |

## 15. 章末の差し替え案

第7章の最後に、次のまとめを追加するとよい。

> AMT写像連鎖は、住所を単一の文字列から単一の実体へ変換する手続きではない。AMT写像連鎖は、表面表現を証拠束へ変換し、言語・履歴・自然地理・行政・郵便・建物・配送の証拠を保ったまま候補を生成し、候補を構造的に比較し、クラスタとして評価し、必要なら保留し、十分な条件を満たす場合にのみPIDを発行し、結果を履歴へ接続する手続きである。
>
> この連鎖は、第6章の住所参照不可能性定理に対する建設的な応答である。完全な単発解決器が存在しないからこそ、AMTは候補、クラスタ、評価、保留、PIDゲート、履歴を分離して扱う。
