# 住所写像論 日本語版 v1 第8章 追加・編集差分案

作成日: 2026-06-06

対象: `docs/address-morphism-theory-ja-v1-master.md` 第8章

目的: 第8章「候補生成と出典政策」を、検証済みのLean定理、GIS検証、住所検証エンジン、自然地理対応、内部品質スコアに合わせて強化するための差し込み文、定義、表、命題、注意点をまとめる。

## 1. 編集方針

第8章では、候補生成を「検索結果を返す処理」ではなく、「後段の構造比較、評価、保留、PID発行、監査のために証拠つき候補集合を作る処理」として書く。

最も重要な線引きは、次の三つである。

```text
候補を生成できる
  != 検証済み住所である
  != PIDを発行できる
```

冒頭に、次を追加するとよい。

> 候補生成は、AMT写像連鎖における最初の安全ゲートである。候補に真の対象が含まれなければ、後段の構造比較、クラスタリング、評価関数、PID発行ゲートはその対象を回復できない。一方で、候補を生成できることは、検証済み住所主張やPID発行を意味しない。AMTでは、候補生成、出典検証、候補表示、検証済み主張、PID発行を明確に分離する。

## 2. 8.1に追加する候補生成三原則

8.1の直後に、次の三原則を追加する。

### 候補生成三原則

| 原則 | 内容 |
| --- | --- |
| 再現率優先 | 真の対象を早く捨てない。 |
| 出典保持 | 各候補に、出典、時刻、言語、変換規則、検索範囲を付ける。 |
| 非昇格 | 弱い候補を、追加条件なしに検証済み主張やPID発行へ昇格しない。 |

追加本文:

> 候補生成では、精度より再現率を優先する。ただし、候補集合の拡大は、出典保持と非昇格原則を伴わなければならない。弱い出典から得られた候補は、候補として保持されるが、単独で検証済み住所、配送可能性、PID発行の根拠にはならない。

## 3. 8.1に追加する候補生成写像

候補生成を、複数出典アダプタの合併として書く。

```text
Gamma_{c,t}(B)
  = union_{i in I} A_i(B, c, t)
```

記号:

| 記号 | 意味 |
| --- | --- |
| \(B\) | 解析・展開された証拠束 |
| \(c\) | 文脈 |
| \(t\) | 時刻 |
| \(A_i\) | 出典アダプタ |
| \(I\) | 利用可能な出典アダプタ集合 |
| \(\Gamma_{c,t}(B)\) | 有限候補集合 |

追加本文:

> 候補生成写像 \(\Gamma_{c,t}\) は、単一の検索器ではなく、複数の出典アダプタの合併として定義される。公式郵便、行政、地図、建物、自然地理、履歴、配送履歴、利用者補助情報は、それぞれ異なる候補を生成する。AMTはこれらを単純に同一視せず、出典メタデータとともに候補集合へ格納する。

## 4. 8.2の出典分類表を拡張する

現行表は良いが、検証文脈を追加するとより強くなる。

| 出典種別 | 強い文脈 | 弱い文脈 | 候補生成 | 検証済み主張 | PID発行 |
| --- | --- | --- | --- | --- | --- |
| 公式郵便データ | 郵便住所、郵便番号、配送区域 | 自然地理、建物内部、旧住所 | 強い | 郵便文脈で強い | 条件付きで強い |
| 行政データ | 管轄、行政地名、公式変更 | 細粒度住所、入口、部屋 | 強い | 管轄文脈で強い | 条件付きで強い |
| 公式地理・地籍データ | 境界、土地、建物、座標 | 表記揺れ、配送可否 | 強い | 地理文脈で強い | 条件付きで強い |
| 地図データ | 施設、道路、自然地物、形状 | 権威性、更新差 | 強い | 単独では注意 | 補助証拠 |
| 建物データ | 階、入口、部屋、用途 | 入手性、非公開性 | 中から強 | 建物文脈で強い | 条件付き |
| 自然地理データ | 山、川、湖、島、湿地、砂漠 | 配送住所、郵便番号 | 強い | 地理文脈で強い | 配送可否とは分離 |
| 歴史データ | 旧住所、改称、行政変更 | 完全性、時刻精度 | 強い | 履歴文脈で強い | 履歴接続に必要 |
| 配送履歴 | 到達可能性、失敗率 | 偏り、プライバシー、非公開性 | 中 | 到達文脈で強い | 補助または監査証拠 |
| 利用者補助情報 | 入口、部屋、慣用名、説明 | 誤入力、虚偽、主観性 | 中 | 単独では弱い | 単独不可 |

追加本文:

> 出典の強さは絶対的ではなく文脈依存である。公式郵便データは郵便住所には強いが、山頂、湖、砂漠、海域、洞窟入口、世界遺産の境界を決める万能ソースではない。逆に、自然地理データは山や川の候補生成には強いが、配送可能性を単独で保証しない。

## 5. 8.3に追加する出典状態モデル

現行のメタデータ定義に、出典検証状態を追加する。

```text
status(q) in {
  accepted,
  provisional,
  unknown,
  rejected,
  stale,
  conflict
}
```

Lean中核に合わせる最小モデルは次である。

```text
SourceValidation = accepted | unknown | rejected
```

論文本体では、実務用に `provisional`, `stale`, `conflict` を追加できる。ただし、Leanで形式化済みなのは最小モデルであると注記する。

追加本文:

> 出典ステータスの最小モデルでは、`accepted` のみが検証済み主張に利用できる。`unknown` と `rejected` は、候補生成の補助には使えても、単独で検証済み住所主張へ昇格できない。実務上はさらに、暫定、失効、鮮度切れ、矛盾状態を扱う必要がある。

## 6. 8.3に追加する候補オブジェクト

候補には、少なくとも次の情報を持たせる。

```text
Candidate = {
  id,
  label,
  entityHint,
  geometry,
  sourceIds,
  sourceTypes,
  sourceStatus,
  language,
  aliases,
  context,
  postalEvidence,
  administrativeEvidence,
  naturalFeatureType,
  historicalEvidence,
  deliveryEvidence,
  quality,
  freshness,
  confidence,
  warnings
}
```

追加本文:

> AMTの候補は、単なる文字列ではない。候補は、ラベル、形状、出典、言語、別名、文脈、郵便証拠、行政証拠、自然地理証拠、履歴証拠、配送証拠、品質、鮮度、警告を持つ構造化オブジェクトである。

## 7. 8.4 多言語・別名展開の補強

現行本文に、次を追加する。

> 多言語展開は、アプリ表示言語および住所表示言語から独立して行う。たとえば、UIが日本語であっても、検索対象がアラビア語、キリル文字、ギリシャ文字、デーヴァナーガリー、タイ文字、ローマ字、現地語、旧地名、観光名であれば、それらを候補生成用に展開する。

さらに、独立証拠と別名展開の違いを明記する。

> ただし、別名展開は独立証拠を増やすものではない。同一出典から派生した翻訳名、ローマ字、略称、アクセント除去表記を複数持っていても、それらは同一出典に相関した候補である。評価関数では、別名の数と独立出典の数を区別する。

## 8. 8.5 自然地理候補の拡張

自然地理候補の対象を、次の表で明確にする。

| 種別 | 形状 | 候補化すべき対象 |
| --- | --- | --- |
| 道路 | 線 | 道路全体、交差点、橋、入口、沿道施設 |
| 川 | 線 | 川全体、岸、橋、合流点、滝、河口、港 |
| 湖、池、貯水池、塩湖 | 面 | 水域、湖岸、港、浜、周辺施設、観測点 |
| 島、群島、環礁、岩礁 | 面または点 | 島全体、港、集落、灯台、近傍施設 |
| 山、谷、洞窟、氷河 | 点、線、面、立体 | 山頂、登山口、稜線、谷入口、洞窟入口、氷河末端 |
| 砂漠、荒野、草原、森林、湿地、氷原 | 面 | 名称領域、管理区域、道路入口、観測点、近傍集落 |
| 遺跡、世界遺産、保護区 | 面または複合 | 登録範囲、入口、管理施設、構成資産 |
| 海域、湾、海峡、海底地物 | 面または線 | 海域名、港、保護区、航路、観測点 |

追加本文:

> 自然地理住所では、対象そのものと到達点を分ける必要がある。「湖」は湖全体を指す場合も、湖畔の施設を指す場合も、北岸を指す場合もある。「山」は山頂、登山口、山小屋、稜線、行政区域のいずれかを指す可能性がある。したがって、自然地理候補生成では、名称だけでなく形状、入口、岸、港、近傍施設、管理施設、観測点を候補化する。

## 9. 8.6 履歴候補の補強

現行本文は正しい。次を追加すると第12章と接続しやすい。

> 履歴候補生成は、旧住所を現在住所へ単純に変換する処理ではない。旧住所は分割、統合、改称、再開発、境界変更、名称再利用により、複数の現在候補へ対応することがある。したがって、履歴候補生成の出力は、単一の現在住所ではなく、履歴グラフ上の候補ノード集合である。

追加表:

| 履歴変化 | 候補生成の扱い |
| --- | --- |
| 改称 | 旧名と新名を同じ履歴系列候補へ接続する。 |
| 分割 | 旧ノードから複数の現在ノードへ接続する。 |
| 統合 | 複数旧ノードを一つの現在ノードへ接続する。 |
| 境界変更 | 空間範囲と行政範囲を分けて候補化する。 |
| 再開発 | 建物、土地、入口、用途の変化を別証拠として扱う。 |
| 名称再利用 | 同名だが別実体の可能性を残す。 |

## 10. 8.7 候補被覆証拠の補強

現行の

```text
CoverageEvidence(s,c,t,C,Q)
```

を、次のように具体化する。

```text
CoverageEvidence(s,c,t,C,Q) =
  {
    input: s,
    context: c,
    time: t,
    candidates: C,
    sources: Q,
    queryVariants,
    searchedRegions,
    sourceStatuses,
    freshnessBounds,
    candidateCaps,
    excludedCandidates,
    licenseConstraints,
    warnings
  }
```

追加本文:

> 候補被覆証拠は、絶対的な世界完全性を主張するものではない。候補被覆証拠は、宣言された出典、検索範囲、時刻、言語展開、件数上限、品質条件、除外理由のもとで、候補生成が監査可能であることを示す証拠である。

## 11. 8.8 失敗モードの整理

現行の失敗モード一覧に、次の対応表を追加する。

| 失敗モード | 推奨結果 | 理由 |
| --- | --- | --- |
| 公式データが存在しない | `candidate-only` or `manual-required` | 公式検証へ昇格しない。 |
| 公式データが古い | `reverify` or `unresolved` | 鮮度不足。 |
| 建物内部データがない | `conditional unresolved` | 入口、階、部屋が必要。 |
| 自然地理境界が揺れる | `ambiguous` | 中心点だけでは危険。 |
| 多言語名が不足 | `expand more` or `unresolved` | 候補欠落の可能性。 |
| 旧住所履歴が不完全 | `ambiguous` | 複数後継候補があり得る。 |
| 配送履歴が偏る | `partial` | 履歴は強いが絶対ではない。 |
| 入力が短すぎる | `ambiguous` | 複数候補が残る。 |
| 入力が複数文脈を混ぜる | `conditional unresolved` | 目的文脈を分離する。 |
| 出典ライセンスが目的に合わない | `rejected for use` | 利用許諾違反を避ける。 |

注:

> ここでの `conditional unresolved` は、独立したLean型ではなく、追加条件を持つ `unresolved` として扱う。

## 12. 内部品質スコアとの接続

第8章に、品質スコアはユーザー表示ではなく内部判定用であると明記する。

追加本文:

> 出典メタデータと候補被覆証拠は、内部品質スコアに渡される。内部品質スコアは、候補表示、再検証、低品質タブ非表示、PID発行ゲート、監査対象選定に使う。ただし、このスコアをそのままユーザーへ表示する必要はない。ユーザーには、必要な場合に「追加確認が必要」「配送可能性は未確認」「地理情報で確認済み」などの状態だけを示す。

追加表:

| 内部判定 | 意味 | ユーザー表示 |
| --- | --- | --- |
| `show` | 表示に十分。 | 通常表示。 |
| `reverify` | 表示できるが再検証対象。 | 必要なら注意表示。 |
| `hide` | 明らかに未解決または無意味。 | 表示しない。 |
| `canSkipSecondVerification` | 安定した都市住所などで二重検証不要。 | 表示しない内部最適化。 |

## 13. 追加すべき命題

### 命題 8.1 候補欠落非回復命題

候補集合 \(C\) に対象 \(x\) が含まれないなら、AMT写像連鎖の後段は \(x\) について安全なPID発行を行えない。

```text
x notin C
  -> not IssueAdmissible(C, x)
```

解説:

> 候補生成の品質は、後段の評価関数の上限を決める。この命題はLeanの `missing_candidate_prevents_issue` と対応する。

### 命題 8.2 出典非昇格命題

出典 \(q\) が `accepted` でないなら、\(q\) だけから検証済み住所主張を構成してはならない。

```text
status(q) != accepted
  -> not SourceVerified(q)
```

解説:

> 未知ソース、拒否ソース、失効ソース、文脈外ソースを検証済み主張へ昇格しないための命題である。

### 命題 8.3 多言語展開相関命題

同一出典に由来する別名集合は、候補再現率を高めるが、独立証拠数として単純加算してはならない。

解説:

> これは、検索能力の向上と証拠評価の厳密性を両立させるために必要である。

### 命題 8.4 no-postal非劣化命題

郵便番号を使わない地域において、強い地理・行政・建物・配送証拠がある場合、郵便番号がないことだけを理由に住所品質を低く評価してはならない。

解説:

> Hong Kong型のno-postal地域、島、極地、自然地理住所、災害時住所に必要な命題である。

### 命題 8.5 自然地理到達点分離命題

自然地理名が指す対象と、配送・到達・表示に使う具体的到達点は一致するとは限らない。

解説:

> 湖そのものと湖畔施設、山そのものと登山口、川そのものと橋、世界遺産の登録範囲と入口を分けるための命題である。

## 14. 本文で避けるべき表現

| 避ける表現 | 理由 | 修正文 |
| --- | --- | --- |
| 候補生成で正解を見つける | 候補生成は探索空間を作るだけ。 | 候補生成で証拠つき候補集合を作る。 |
| 出典が多いほど正しい | 同一出典由来の別名がある。 | 独立出典と派生別名を分ける。 |
| 公式郵便データがあれば住所は確定する | 郵便以外の文脈がある。 | 郵便文脈では強い証拠になる。 |
| OSMで見つかったから検証済み | 地図ソースと公式検証は違う。 | 地図候補または地理証拠として扱う。 |
| 郵便番号なしは低品質 | no-postal地域がある。 | 別の検証モードを使う。 |
| 自然地理は中心点でよい | 線・面・立体では不十分。 | 到達点、入口、岸、近傍施設を候補化する。 |
| 候補が一つならPID発行できる | 品質、鮮度、リスク、監査が必要。 | PID発行ゲートを通す。 |

## 16. 章末の差し替え案

第8章の最後に、次のまとめを追加するとよい。

> 候補生成は、AMTの安全性を決める最初の大きな段階である。真の対象が候補集合に含まれなければ、後段の構造比較、クラスタリング、評価関数はそれを回復できない。一方で、候補を生成できることは、検証済み住所主張やPID発行を意味しない。AMTでは、公式郵便、行政、地図、建物、自然地理、履歴、配送履歴、利用者補助情報を、出典メタデータとともに候補集合へ格納し、文脈に応じて評価する。
>
> 特に、世界規模の住所解決では、多言語地名、旧住所、島、山、川、湖、砂漠、湿地、氷原、遺跡、世界遺産、海域、郵便番号を持たない地域を扱う必要がある。これらを単一の郵便住所モデルに押し込むのではなく、候補生成、出典検証、地理検証、配送可能性、PID発行を分離して扱うことが、AMTの実装上の強みである。
