# 住所写像論 日本語版 v1 第21章 追加・編集差分案

対象: 第21章「検証と再現性」

本差分案は、第21章を、住所写像論全体の証拠台帳として強化するための本文案である。中心方針は、Lean、GIS、実装テスト、ベンチマーク、セキュリティレビュー、未検証主張を混ぜず、それぞれの役割と限界を明確にすることである。

## 1. 章冒頭に追加する要約

第21章の冒頭に、次を追加するとよい。

> 本章では、住所写像論の各主張をどのように検証し、どのように再現可能に記録するかを定義する。AMTは形式理論、GIS、郵便データ、実装、セキュリティ、運用観測にまたがるため、単一の検証方法で全体を保証することはできない。したがって本章では、主張を検証様式ごとに分類し、証拠ファイル、実行コマンド、対象データ、結果、限界、反証時の書き換え方を対応付ける。

続けて、次を入れる。

> 本稿で「検証済み」と言う場合、それは常に特定の検証様式と対象範囲に依存する。Leanで証明された命題は形式モデル内の命題であり、GISで検証された結果は対象データと出典範囲内の空間的検証であり、実装テストで通った結果は指定されたテストケース内の再現性である。

## 2. 21.1に「検証多元性原則」を追加する

21.1の末尾に、次を追加する。

### 原則21.1 検証多元性原則

> AMTの主張は、形式命題、地理空間命題、実装命題、運用命題、セキュリティ命題、ベンチマーク命題に分解され、それぞれに異なる検証方法を割り当てる必要がある。

本文案:

> たとえば、非単射観測の不可能性はLeanで検証できる。一方、湖、島、川、山、砂漠、湿地、氷河などの自然地物を住所候補として扱えるかは、GISデータと実装テストで検証する必要がある。さらに、配送可能性や居住資格は、地理空間だけでなく、配送業者、credential、鮮度、失効、同意スコープを含む運用検証を必要とする。

注意書き:

> ある検証方法で得られた証拠は、その方法が扱う対象を越えて拡張してはならない。Leanの証明は地図データの正しさを保証せず、GISの妥当性は居住や所有の真実性を保証せず、実装テストの成功は世界全体の網羅性を保証しない。

## 3. 21.1に証拠階層を追加する

21.1または21.6に、次の表を追加するとよい。

| 証拠階層 | 役割 | 限界 |
|---|---|---|
| 形式証明 | 不可能性、安全性、同値類、発行条件を検証する。 | 現実データの完全性は扱わない。 |
| 機械可読GIS証明書 | GIS検証結果を数値条件として再確認する。 | 個々の地物の現実一致は出典とGIS検査に依存する。 |
| 実装テスト | パイプライン、API、ZK公開面、エラー処理を検証する。 | 代表ケースであり世界網羅ではない。 |
| ベンチマーク | 商用API比較、多言語検索、国別品質を評価する。 | データセットと指標に依存する。 |
| セキュリティレビュー | 漏洩、改ざん、replay、linkability、過剰開示を検証する。 | 実運用の全攻撃を網羅しない。 |
| 運用観測 | 配送成功、失敗理由、鮮度、現地更新を観測する。 | サンプリング偏りとプライバシー制約がある。 |

## 4. 21.2をLeanで証明できる主張表へ整理する

21.2には、次の表を追加するとよい。

| 主張 | Lean上の対応 | 本文での扱い |
|---|---|---|
| 非単射観測では条件なし完全解決器は存在しない | `no_condition_free_perfect_resolver` | 定理として保持する。 |
| 正規化衝突では失われた差を復元できない | `normalization_collision_prevents_perfect_resolution` | 定理として保持する。 |
| 二次元射影衝突では垂直実体を区別できない | `projection_collision_prevents_vertical_resolution` | 定理として保持する。 |
| unresolvedは誤った実体を発行しない | `unresolved_emits_no_false_entity` | 安全側状態として説明する。 |
| 発行には品質、鮮度、リスク条件が必要 | `issue_if_admissible_requires_conditions` | PID発行ゲートの根拠にする。 |
| 同値類PIDは参照保存的変更に安定 | `class_pid_invariant_under_ref_equivalence` | 表記揺れに対する安定性として説明する。 |
| GIS証明書は数値予算を満たす | `current_gis_certificate_accepted` | GIS結果の機械可読な再確認として扱う。 |

続けて、次の制限を明記する。

> これらのLean定理は、AMTの形式モデルに関する命題である。現実世界の住所、郵便データ、地図データ、居住事実、所有事実、配送成否を直接証明するものではない。

## 5. 21.3をGIS検証の対象表へ整理する

21.3に、次の表を追加する。

| GIS対象 | 検証項目 | 失敗時の扱い |
|---|---|---|
| 国境・行政区域 | 座標範囲、ポリゴン、境界、重複、出典 | `revalidation-required` または `unresolved` |
| 自然地物 | 地物型、代表点、ポリゴン、周辺関係、出典 | 自然住所候補を弱める |
| 島・湖・川・山 | ラベル点と形状の分離、階層関係 | 候補順位を下げる |
| 砂漠・湿地・氷河・荒野 | land-cover、地物名、範囲 | 部分住所として扱う |
| 遺跡・世界遺産・公園 | POI、保護区域、施設境界 | 住所本文ではなく周辺文脈として扱う |
| 配送可能区域 | 区域内判定、境界条件、鮮度 | 配送可能性を未確定にする |

本文案:

> GIS検証は、候補生成と空間述語の妥当性を支える。しかし、GIS検証だけで住所の社会的同一性、居住資格、所有権、実配送成否を証明することはできない。これらはcredential、配送履歴、監査、法的出典を必要とする。

## 6. 21.4を実装テストの対象表へ整理する

21.4に、次の表を追加する。

| 実装領域 | 検証内容 | 代表テスト |
|---|---|---|
| 候補生成と自然住所 | 海、山、湖、川、滝、島、砂漠、湿地、氷原など | `naturalAddress.test.ts` |
| 出典メタデータ | postal source URL、ライセンス方針、OSSソース | `postalSourceMetadata.test.ts` |
| 品質スコア | 内部スコア、低品質注意、ユーザー非表示 | `addressQualitySummary.test.ts`, `GridDetailPanel.test.ts` |
| PID監査 | 候補生成、クラスタ、unresolved判定、履歴更新、PID発行 | `pidIssuanceAudit.test.ts` |
| PID履歴 | update、merge、split、lineage preservation | `pidLifecycleProof.test.ts` |
| ZK公開面 | nullifier、AOID所有、地域所属、品質しきい値、鮮度 | 各ZK proof test |
| API境界 | MCP、AMN envelope、Polkadot、freshness root | `coreRoutes.test.ts` |

本文案:

> 実装テストは、形式証明では扱えない具体的な退行、漏洩、例外、境界条件を検出する。したがって、Leanで定理が通っていても、対応する実装テストを持つべきである。

注意:

> 実装テストの通過は、テスト対象の挙動を示す。世界中の全住所、全言語、全出典、全配送事業者に対する完全性を意味しない。

## 7. 21.5に「未検証主張処理プロトコル」を追加する

21.5の冒頭に、次を追加する。

### 原則21.5 未検証主張明示原則

> 未検証の主張は、断定してはならない。ただし、削除するだけでなく、未検証理由、検証可能化の方法、反証時の書き換えを記録する。

本文案:

```text
UnverifiedClaimState =
  not-formalizable-yet
  needs-dataset
  needs-gis-source
  needs-operational-observation
  needs-legal-review
  needs-security-audit
  deliberately-out-of-scope
```

説明:

> たとえば、「世界中すべての島名を認識できる」という主張は、現時点では `needs-dataset` と `needs-gis-source` に分類される。「住所の真の社会的同一性を完全に判断できる」という主張は、`needs-operational-observation` と `needs-legal-review` に分類され、さらに理論的には不可能性定理により弱める必要がある。

表として、次を追加する。

| 未検証主張 | 状態 | 検証可能化 |
|---|---|---|
| 世界中すべての住所を完全候補生成できる | `needs-dataset` | 国別、地物型別、言語別ベンチマークを作る。 |
| 商用APIに全項目で勝てる | `needs-dataset` | Loqate等との項目別固定ベンチマークへ分解する。 |
| 公式データが常に最新 | `needs-operational-observation` | 鮮度、更新日時、失効条件を記録する。 |
| 社会的連続性を完全判断できる | `needs-legal-review` | 履歴グラフと法的出典に限定する。 |
| ZKPだけで住所真実性を保証できる | `deliberately-out-of-scope` | ZKPは秘匿証明であり真実性はcredentialとAMT証拠に依存すると書く。 |

## 8. 21.6の再現性マップを拡張する

21.6の表を、次の形式へ拡張するとよい。

```text
ClaimRecord = {
  claimId: string
  claimText: string
  verificationClass: lean | gis | implementation | benchmark | security | operational | unverified
  evidenceFile: string
  commandOrDataset: string
  result: pass | fail | partial | pending | out-of-scope
  limitation: string
  rewriteIfFailed: string
  nextVerificationStep: string
}
```

本文案:

> 再現性マップは、単なるテスト一覧ではない。主張、検証方法、証拠、限界、反証時の書き換えを同じ行に置くことで、論文の主張がどの範囲で成立するかを読者が追跡できるようにする。

実例として、次を入れる。

| claimId | 主張 | 検証方法 | 証拠 | 結果 | 限界 |
|---|---|---|---|---:|---|
| AMT-21-LEAN-001 | 非単射観測では完全解決不能 | Lean | `formal/AMTCore.lean` | pass | 形式モデル内の命題 |
| AMT-21-GIS-001 | GIS警告予算が範囲内 | GIS + Lean証明書 | `gis-warning-budget-report.json` | pass | 登録済みソース範囲内 |
| AMT-21-PID-001 | 128-bit PIDの衝突リスクが予算内 | 計算 | `pid-collision-risk.json` | pass | 発行上限と乱択仮定に依存 |
| AMT-21-IMPL-001 | 代表実装テストが通る | 実装テスト | selected Node tests | pass | 代表ケースのみ |
| AMT-21-BENCH-001 | 商用API比較 | ベンチマーク | 未作成 | pending | 固定データセットが必要 |

## 9. 反証時の書き換え規則を追加する

21.6の末尾に、次を追加するとよい。

### 原則21.6 反証時書き換え原則

> 検証が失敗した場合、AMTは主張を隠すのではなく、対象範囲、前提条件、しきい値、未解決条件、再検証条件を更新する。

本文案:

> たとえば、ある国で郵便番号検証が失敗した場合、「郵便番号検証エンジンは全世界で強い」とは書かない。代わりに、「当該国は候補生成のみ」「当該国は手動確認優先」「当該国は公式ソース待ち」「当該国は地理検証のみ」などへ書き換える。失敗は論文の弱点ではなく、AMTの安全側設計を発動する入力である。

## 10. 本文から避けるべき表現

第21章では、次の表現を避ける。

| 避ける表現 | 理由 | 置換案 |
|---|---|---|
| 全て検証済みである | 対象範囲が不明確 | 検証様式ごとに検証範囲を示す |
| Leanで現実住所の正しさを証明した | Leanの対象を越える | Leanで形式命題を証明した |
| GISで住所の真実性を証明した | 社会的事実を扱っていない | GISで空間関係と出典範囲を検査した |
| 実装テストが通ったので世界対応済み | テスト範囲の過大解釈 | 代表ケースで再現性を確認した |
| 商用APIに負けない | ベンチマーク未完 | 項目別ベンチマークで比較する |
| ZKPで住所が正しいと証明できる | ZKPの役割を誤解する | ZKPで住所由来属性を秘匿証明できる |

## 11. 第22章への接続文

第21章の末尾に、次を追加すると第22章へ自然につながる。

> なお、再現性は安全性そのものではない。再現可能な実装であっても、漏洩、replay、linkability、issuer偽装、過剰開示、登録濫用があれば安全な住所システムとはいえない。したがって次章では、AMTを悪用や攻撃から守るためのセキュリティ、監査、ガバナンス上の制約を整理する。

## 12. 第21章の推奨構成

第21章は、次の順に整理すると読みやすい。

1. 検証多元性原則
2. Leanで検証できる形式命題
3. GISで検証できる空間命題
4. 実装テストで検証できるパイプライン命題
5. ベンチマークで検証すべき性能主張
6. 未検証主張処理プロトコル
7. 再現性マップ
8. 反証時の書き換え規則
9. 第22章への接続

この構成により、第21章は単なる検証メモではなく、住所写像論全体の研究信頼性を支える方法論の章になる。
