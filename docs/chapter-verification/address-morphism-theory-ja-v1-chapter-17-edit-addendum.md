# 住所写像論 日本語版 v1 第17章 追加・編集差分案

対象: 第17章「評価関数、品質、評判」

本差分案は、第17章をより数学的に正確で、検証結果と実装に接続しやすい形へ修正するための本文案である。中心方針は、評価関数、品質スコア、配送履歴、評判を「真理」ではなく「発行を安全に制御する証拠モデル」として扱うことである。

## 1. 章冒頭に追加する要約

第17章の冒頭に、次を追加するとよい。

> 本章では、AMTにおける評価関数、品質、評判を扱う。評価関数は、候補やクラスタの証拠上の強さを測るためのものであり、住所の真理そのものではない。品質スコアは、ユーザーに直接表示する点数ではなく、候補表示、注意表示、再検証、追加証拠要求、PID発行停止の内部制御に使う。

続けて、次を入れる。

> 第17章の目的は、最も高いスコアの候補を常に選ぶことではない。目的は、十分な証拠がある候補だけを安全に選び、証拠が不足する場合には `ambiguous` または `unresolved` を返し、PID発行を保留することである。

## 2. 17.1を「評価非真理原則」として強化する

第17.1節の末尾に、次の原則を追加する。

### 原則17.1 評価非真理原則

> 評価関数の出力は、候補またはクラスタに対する証拠上の選好であり、実世界における住所同一性の真理値ではない。

本文案:

> 高い評価スコアは、候補を上位に表示する根拠にはなる。しかし、それだけでPIDを発行する根拠にはならない。PID発行には、候補被覆、候補間マージン、品質、鮮度、リスク、履歴整合性、監査可能性を含む発行ゲートが必要である。

Lean対応として次を入れる。

```text
IssueAdmissible
issue_if_admissible_requires_conditions
issue_if_not_admissible_abstains
```

意味:

> 発行されたなら発行条件が揃っている。条件が揃わなければ、解決器は発行せず保留する。

## 3. 17.2の証拠重みモデルを「例」に限定する

現在の本文には、シグモイドを使った評価式がある。これはよいが、AMTが特定の統計モデルを強制するように見えないように、次の注意を入れる。

> 以下の式は評価関数の一例であり、AMTが特定の統計モデルを要求するものではない。実装は、ロジスティック回帰、ベイズ更新、ランキングモデル、ルールベース、学習済みモデル、またはこれらの混合を使い得る。AMTが要求するのは、支持証拠、矛盾、鮮度、出典、文脈適合性、リスクを分離して監査可能に扱うことである。

記法は、本文の可読性を優先して次のように書く。

```text
Score(context, time, cluster)
  = combine(
      supportEvidence,
      sourceAuthority,
      freshness,
      contextFit,
      history,
      conflictPenalty,
      riskPenalty
    )
```

数式を残す場合は、直後に次を加える。

> この式の値は、真理値ではなく、選択候補の証拠強度である。

## 4. しきい値とマージンの命題を追加する

17.2または17.8の近くに、次の命題を入れるとよい。

### 命題17.2 しきい値・マージン必要命題

> 自動解決またはPID発行の候補選択では、最良候補のスコア条件だけでなく、第二候補に対する十分な分離が必要である。

証明の考え方:

> 最良候補と第二候補がほぼ同じ証拠強度を持つ場合、最良候補を選ぶことは過剰決定になる。したがって、十分なマージンがない場合は `ambiguous` とするべきである。

Lean対応:

```text
score_selection_requires_threshold
tied_evidence_prevents_score_selection
```

本文案:

> しきい値は低品質候補の選択を防ぎ、マージンは近接タイの強制選択を防ぐ。これにより、AMTは候補表示とPID発行を分離できる。

## 5. 17.3の公式性と鮮度を分離する

第17.3節の `SourceScore` を、次のような成分分解として書くとよい。

```text
SourceQuality(source, time, region, kind) = {
  authority,
  freshness,
  coverage,
  granularity,
  license,
  reliability,
  updateCadence
}
```

本文案:

> 公式性は強い証拠であるが、古い公式データは危険である。一方で、新しい非公式データは現地変化を反映している場合があるが、法的住所や公式境界を保証しない。したがって、公式性と鮮度は一つの点数に潰さず、別成分として扱う。

反例を追加する。

> 公式住所台帳が更新されていない新築、災害後の一時住所、移転済みロッカー、氷河や湿地の変化、海岸線の変化では、公式性と鮮度が衝突し得る。

## 6. 17.4の記法を読みやすくする

現在の本文では、品質スコアを次のように置いている。

```text
Q(c,t,r,l,tau)
```

ここで `t` と `tau` が近く、時刻と対象種別が読みにくい。次のように変更するとよい。

```text
Q(context, time, region, language, kind)
```

または短く:

```text
Q_ctx,time(region, language, kind)
```

本文案:

> 品質スコアは、国や地域だけでなく、言語、対象種別、用途、時刻、出典、表示形式に依存する。都市住所に強いモデルが、島、山地、砂漠、極地、湿地、氷原、文化財住所に強いとは限らない。

## 7. 17.5の環境分類を増やす

第17.5節の列挙に、次を追加すると第16章とつながる。

```text
EnvironmentKind = {
  urban,
  rural,
  island,
  mountain,
  desert,
  sparse_natural,
  water,
  wetland,
  polar,
  cultural_site,
  vertical_building
}
```

本文案:

> AMTの品質評価は、環境ごとの失敗モードを分ける。都市では垂直参照と入口が問題になり、田舎では表記の粗さと道路名不足が問題になり、島では多言語名と港が問題になり、山地や砂漠では自然地物とアクセス点が問題になり、水域では湖岸、港、滝、橋、流域が問題になり、極地では基地と移動する地形が問題になる。

表として次を入れる。

| 環境 | 主な失敗モード | 改善に必要な証拠 |
|---|---|---|
| 都市 | 同名ビル、入口違い、部屋、テナント変更 | 建物内部、入口、テナント、配送履歴 |
| 田舎 | 粗い住所、道路名不足、広い敷地 | 地図、集落名、ランドマーク、地域ルール |
| 島 | 多言語名、港、無人島、礁 | 島名辞書、海図、港、行政所属 |
| 山地 | 山名、登山口、山小屋、アクセス不足 | 自然地理、標高、登山道、アクセス点 |
| 砂漠 | 広域地物、座標依存、出典不足 | 自然地名、座標、土地被覆、観測点 |
| 水域 | 湖岸、川区間、滝、橋、港 | 水系、湖岸、港、橋、危険区域 |
| 極地 | 基地、氷原、地形変動、住所不足 | 研究基地、極地データ、衛星データ |
| 文化地物 | ラベル点、法的境界、入口違い | 文化財境界、管理者、入口、施設情報 |
| 垂直建物 | 同じ2D座標の階・部屋違い | 階、部屋、入口、ロッカー、内部経路 |

## 8. 17.6の配送履歴と評判を慎重に書く

第17.6節に、次の命題を追加する。

### 命題17.3 評判分離命題

> 配送履歴に基づく評判は、候補評価の一成分であり、住所同一性、公式性、法的住所、配送可能性の完全証明ではない。

本文案:

> 配送成功率、返品率、受取確認、配送事業者の記録は、実際の到達可能性を示す強い証拠になり得る。しかし、配送成功は住所表記の意味論的正しさを完全に証明しない。配送員の経験、電話確認、補足メモ、近隣知識により成功した場合があるためである。

評判関数は次のように分ける。

```text
Reputation(time, entity) = combine(
  deliverySuccesses,
  deliveryFailures,
  returnRate,
  confirmationStrength,
  carrierDiversity,
  freshness,
  fraudReports,
  dataVolume
)
```

注意書き:

> 評判にはデータ量の偏りがある。配送量が多い都市ほど評判が安定し、疎地域や島や極地では評判が不安定になりやすい。したがって、評判スコアにはサンプル数や地域補正を含める必要がある。

Lean対応として次を入れる。

```text
positive_evidence_monotone_reputation
```

ただし、直後に次を置く。

> このLean命題は、正の証拠成分の単調性だけを支える。評判モデル全体の妥当性は、実データでの較正が必要である。

## 9. 17.7のunresolved履歴を品質改善モデルにする

第17.7節に、次の表を追加する。

| unresolvedが多い場所 | 可能な原因 | 改善策 |
|---|---|---|
| 山地・砂漠 | 自然地物候補不足、アクセス点不足 | 自然地理ソース、登山道、観測点、基地データを追加 |
| 都市 | 垂直参照不足、入口不足、同名建物 | フロア、部屋、入口、テナント、建物内部情報を追加 |
| 島 | 多言語名衝突、港情報不足 | 別名、海図、港、行政所属を追加 |
| 水域 | 湖岸、川区間、滝、橋の不明瞭さ | 水系、港、橋、流域、危険区域を追加 |
| 極地 | 基地・氷原・移動地形データ不足 | 研究基地、衛星データ、極地地名集を追加 |
| 郵便番号弱地域 | 公式住所・郵便ソース不足 | 公式住所データ、地域ルール、地図ソースを追加 |

本文案:

> unresolvedは失敗ログではなく、安全な非発行状態であり、同時にデータ改善の観測である。ある地域、言語、対象種別でunresolvedが集中する場合、AMTはその集中を候補生成、出典、品質しきい値、表示方法の改善に使う。

## 10. 17.8を品質しきい値ゲートとして書き直す

第17.8節を次のように整理する。

```text
QualityOK(candidate, context, region, kind)
```

発行ゲート:

```text
IssueOK(candidate)
  = CandidateCovered(candidate)
    and ScoreOK(candidate)
    and MarginOK(candidate)
    and QualityOK(candidate)
    and FreshnessOK(candidate)
    and RiskOK(candidate)
    and HistoryOK(candidate)
```

本文案:

> 品質しきい値は、候補表示ではなく、PID発行や自動解決の安全条件として特に重要である。一般検索では低品質候補を注意付きで表示できる場合がある。しかし、PID発行、本人確認、配送可能性、災害支援、権限付与では、品質しきい値を高く設定する必要がある。

Lean対応:

```text
low_quality_prevents_issue
stale_freshness_prevents_issue
high_risk_prevents_issue
high_energy_prevents_issue
low_margin_prevents_issue
```

## 11. 17.9の品質スコア利用方針を強める

第17.9節に、次の方針を明記する。

> 品質スコアはユーザーに直接表示しない。ユーザーに表示するのは、スコアそのものではなく、操作上必要な状態である。

ユーザー向け状態:

```text
DisplayDecision = {
  show,
  warn,
  reverify,
  hide,
  request_more_evidence
}
```

本文案:

> 生の点数を表示すると、ユーザーに誤った確実性を与える可能性がある。また、地域や言語に対する不当な印象を生む可能性がある。さらに、攻撃者が入力を調整してしきい値を探索する可能性もある。したがって、品質スコアは内部制御に使い、ユーザーには注意、再検証、追加情報要求などの行動可能な状態として提示する。

## 12. 第17章で避けるべき表現

| 避ける表現 | 理由 | 修正案 |
|---|---|---|
| 高スコアなら正しい | スコアは真理ではない | 高スコアは証拠上の選好である |
| 配送成功は住所の正しさを証明する | 補足情報や配送員知識で成功することがある | 配送成功は評判証拠である |
| 公式ソースなら常に安全 | 古い公式データがあり得る | 公式性と鮮度を分離する |
| 新しい地図データなら公式よりよい | 法的住所を保証しない | 鮮度と公式性を別成分にする |
| 品質スコアをユーザーに見せる | 誤信、不公平感、しきい値探索の危険 | show/warn/reverify/hideとして提示する |
| どの国でも同じ品質モデルでよい | 地域・制度・言語差が大きい | 地域別・言語別・対象種別別に評価する |

## 13. 章末まとめ案

第17章の末尾を次のように締めるとよい。

> 本章では、AMTにおける評価関数、品質、評判を定式化した。評価関数は候補の証拠強度を測るが、住所の真理そのものではない。品質スコアは、国、言語、地域、対象種別、出典、鮮度、履歴、リスクに依存し、ユーザーへ直接表示する点数ではなく、非表示、注意表示、再検証、追加証拠要求、PID発行停止の内部制御として用いられる。

続けて次を入れる。

> 配送履歴と評判は、実際の到達可能性を示す強い証拠になり得るが、住所同一性や法的住所の完全証明ではない。AMTは、評判を品質の一成分として扱い、公式性、候補被覆、履歴整合性、鮮度、リスクと分離して管理する。

第18章への橋渡し:

> 次章では、AMT本体と暗号拡張の境界を扱う。品質しきい値や評判を秘匿証明する応用はあり得るが、それはAMT本体ではなく、AMTが生成した意味論的属性を利用する別層である。

## 14. 最終的な編集方針

第17章は、次の五つを柱にすると強い。

1. 評価関数は真理ではなく証拠上の選好である。
2. PID発行には、しきい値、マージン、品質、鮮度、リスク、履歴、監査が必要である。
3. 品質スコアは地域、言語、対象種別、環境、出典、表示品質に依存する。
4. 配送履歴は評判証拠であり、真理ではない。
5. 品質スコアはユーザーに直接表示せず、内部安全制御として使う。

この修正により、第17章は単なるスコアリング章ではなく、AMTの安全な解決・非発行・改善サイクルを定義する章になる。
